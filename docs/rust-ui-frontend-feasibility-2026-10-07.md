# Rust/UI frontend migration feasibility — 2026-10-07

**Decision research, not a migration authorization.** Target: preserve JasonShell's current Windows primary-monitor shell appearance and behavior while replacing Svelte/TypeScript/Tauri with the components advertised at <https://rust-ui.com/docs/components>. In this document “remove Tauri” means remove the Tauri host/runtime/API, not merely rename a frontend dependency. Research checked against this checkout on 2026-10-07; external documentation is subject to revision. No target runtime was built or benchmarked.

## Executive answer

**Technically possible to build a Rust-authored frontend using selected Rust/UI components and a Dioxus desktop host, but not a drop-in port or a guaranteed memory/speed improvement.** Rust/UI is a copy/paste Dioxus **HTML/CSS component registry**, not a Windows shell, window manager, or browser-free native widget toolkit [R1–R3]. Dioxus desktop uses a system WebView; on Windows, a WebView2-based desktop path still carries browser/DOM/CSS and possibly JavaScript dependencies. Dioxus also documents an **experimental** native/Blitz renderer, not a proven replacement for these surfaces [R3]. Removing Tauri alone therefore does **not** establish removal of WebView2, elimination of JS, or lower memory. If “100% parity, Tauri-free and WebView-free” is a hard conjunction, the linked catalog cannot by itself meet it; a separate native renderer and extensive custom UI/native integration would be required.

**Recommendation:** do not green-light a wholesale port on framework preference or component count. Keep the current stack as the control; optimize existing per-surface lifecycle and native hotspots, then prototype a Tauri-free Dioxus/WebView2 host for one low-risk surface plus a shell-window/AppBar proof, and measure both. Only pursue a browser-free native alternative if removing WebView2 is itself a stated requirement and prototype parity/performance gates are passed. Preserve the current build as rollback throughout.

## What exactly is being replaced?

| Layer | Existing | Proposed meanings, which must not be conflated |
|---|---|---|
| UI authoring | Svelte 5/TS/CSS, WebGL canvas, DOM integrations | Rust/UI code is Rust/RSX components plus Tailwind CSS; its catalog supplies controls, **not** complete JasonShell skins/workflows [R1,R2]. |
| Desktop host | Tauri 2 manages many labeled `WebviewWindow`s, state, scoped commands/events, plugin dialog, lifecycle [L1,L2] | Dioxus desktop removes Tauri but retains a system webview; its desktop renderer is not equivalent to the experimental native renderer [R3,R4]. |
| Rendering | WebView2 on Windows [R5] | Dioxus desktop still renders HTML/CSS in a system webview; Rust components may execute native-side while DOM updates require a webview bridge/interpreter. This does not imply every component needs bespoke JS, nor that there is zero JS/browser runtime [R3,R4]. |
| OS authority | Rust/Win32: HWNDs, AppBars, DWM, OLE, hooks, ConPTY, audio, native capture | Must remain Rust/Win32 with **new host adapters**, identity checks and cleanup. No Rust/UI component implements OS AppBar ownership. |

The catalog specifically describes itself as “copy-and-paste components” for Dioxus fullstack **web apps**; examples include Button, Context Menu, Data Grid, Dialog, Dropdown Menu, Tabs and Tailwind animation wrappers [R1]. Its README describes Dioxus + Tailwind v4, code copied into the application rather than a crate installed as an opaque UI framework, and states MIT for the repository [R2]. **Licensing gate:** check the exact revision and licenses/attributions of every copied component and transitive assets before distribution; the catalog index contains at least one description calling a `Command` component “for Leptos,” so per-component Dioxus compatibility must be verified rather than assumed [R1]. Catalog maturity, desktop behavior, exact pinned revisions, keyboard/a11y behavior and maintenance cadence have not been certified by this research.

## Parity by surface: controls versus shell semantics

“Candidate” means the catalog provides a **primitive** to adapt, not a parity certification. Full visual parity includes themes, exact geometry, hover/focus, keyboard and accessibility, state, timing, reduced motion, high DPI and native behavior. Current runtime owns **primary-monitor** AppBars only; snipping captures enumerated monitors without extending shell ownership. Workspace restoration/startup execution and automation forwarding are **not** current behaviors [L10].

| Current surface / representative files | Rust/UI candidate | Irreducible bespoke/native parity work |
|---|---|---|
| Top/bottom bars; `TopBar.svelte`, `BottomBar.svelte` | Button, Tooltip, Dropdown, Menu, Tabs | Primary-monitor `SHAppBarMessage` reservation/rollback, Explorer taskbar coordination, edge resize, fullscreen guard, task tile grouping, reorder/hover ticker/focus and Windows z-order. |
| Quick Launch, task preview/gallery; `QuickLaunchPanelSurface.svelte`, `TaskPreviewSurface.svelte`, `TaskGallerySurface.svelte` | Card, Scroll Area, Context Menu | Explorer pins/launch, validated HWND/PID window actions, DWM live/captured thumbnails and captured fallback, nonce/revision/request-id lifecycle, actual multi-window layouts and DPI. |
| Stack Browser/Git/text editor; `StackPopupSurface.svelte`, `StackTextEditor.svelte`, `src/features/stack-browser/stackTextEditorAdapter.ts` | Data Grid, Tree-like custom rows, Dialog, Menus | Filesystem/Git policy, dirty-editor guards, virtualized folder viewport, native Shell/OLE outbound drag, incoming drops, and CodeMirror 6 editor semantics/IME/language extensions. A generic input/textarea is not CodeMirror parity. |
| Persistent terminal and Stack terminal; `TerminalPanelSurface.svelte`, `StackTerminalPane.svelte`, `terminal_panel.rs` | Tabs, Scroll Area | ConPTY/PTY lifecycle plus xterm 6 rendering, selection, resize, escape sequences, unicode, keyboard, replay, search, links and optional WebGL; replacing xterm with plain text fails behavior parity. |
| Quick Commands, search, process manager; command/search/process surfaces | Command, Input, Table, Data Grid | Native process/Everything/app/window sources, bounded output/status, guarded termination and verified identity; virtualization and native command-policy boundaries. |
| Audio, calendar, settings, tray, speech | Slider, Calendar/Date Picker, Forms, Menus | Windows audio/tray/notifications, hotkey-registration rollback, model import, clipboard and native pickers; `src/lib/speechIndicatorOrb.ts` uses WebGL, shader and context-loss fallback, not a catalog icon. |
| Snipping; `SnipOverlaySurface.svelte`, `SnipPreviewSurface.svelte`, `src-tauri/src/snipping/` | Buttons and overlay chrome | Frozen monitor captures, trusted first-pointer monitor binding, transparent/nonactivating overlay/preview HWNDs, per-instance authorization, binary PNG transport, clipboard truthfulness and path-free native PNG save. |

**Concrete boundary:** Rust/UI offers a dropdown primitive, but `src-tauri/src/appbar.rs` still owns AppBar reservation; switching component libraries cannot implement or safely clean up that reservation. Tauri-free WebView retains xterm/CodeMirror/WebGL **only if** the new host's webview integration, bundled JS/assets, window policies and message bridge make those DOM dependencies work; a true browser-free renderer loses these ready-made integrations and needs replacement widgets or explicitly hosted webviews (which forfeits a strict WebView-free target).

## Host and security architecture options

| Option | Benefits | Cost / fit |
|---|---|---|
| **A. Retain Tauri/Svelte; measure and optimize** | Lowest regression risk; current CSS/JS editor/terminal and security scopes survive; target slow/idle surfaces first. | Does not satisfy Tauri-free/Rust-UI authoring. May be the best performance result; prove with release data. |
| **B. Dioxus + Rust/UI desktop, no Tauri** | Rust UI authoring and selected copied controls; Win32 services can be retained through ports. | Still a system WebView and CSS/DOM; entirely new host/IPC/lifecycle/security and Svelte rewrite. Windows WebView2 elimination is **not** a benefit. |
| **C. Stage a Rust/UI/Dioxus web renderer inside existing Tauri** | Lets team validate visual components, terminal/editor interoperability and styling incrementally while old host owns native windows. | Temporary duplicate frameworks/assets and potential memory regression; does **not** meet remove-Tauri objective; isolate experimental surfaces and avoid two authorities over one AppBar. |
| **D. Browser-free native GUI (e.g., iced 0.14 with `iced_wgpu` or software fallback)** | Can remove WebView2 *if every surface and embed is native*, potentially reduce webview process overhead [R6]. | Rust/UI's Dioxus/HTML/Tailwind components cannot simply run in iced. Rebuild styling, virtual lists, text editor, terminal, WebGL orb and accessibility; native GPU allocations remain; high-risk HWND/event-loop integration. Dioxus native/Blitz is experimental [R3]. |

Recommended boundaries for any B/D experiment: `ShellHost` owns main-thread windows, HWND identity, surface lifetime, event-loop integration and AppBar rollback; `NativeServices` encapsulates taskbar/DWM, OLE/drag, ConPTY, hotkeys, snip/picker/clipboard and validated OS operations; `SurfaceTransport` exposes typed requests, scoped events, deadlines and cancellation; `Presentation` only holds view state and receives opaque IDs (not arbitrary HWNDs, filesystem paths or monitor authority). Ensure one authoritative owner per AppBar/overlay, generation IDs and a deterministic startup/exit recovery path. Desktop framework windows must permit real HWND extraction and main-thread OLE callbacks without creating unsafe nested event loops; prove this before translating 39 Svelte files. Keep Win32 process, DWM and file-operation identity revalidation native-side. The current snip capabilities (`src-tauri/capabilities/snipping-{top-bar,overlay,preview}.json`) and legacy-shell capability require an explicit least-privilege replacement; a new IPC transport is not automatically safer [L9].

Persistence migration is a separate compatibility problem: `src/lib/{themes,shellPreferences,searchRanking,searchPanel,topBarControls}.ts` use browser localStorage for UI state, with theme synchronization across views; native `settings.rs`, `workspaces.rs`, `speech_model_install.rs` own other on-disk state [L6,L11]. Webview origin/profile changes can make old localStorage invisible. Inventory exact keys, versions/defaults and profile path, then implement reversible, bounded import or opt-in reset with no unexpected data loss. Preserve installed speech model generations and existing settings/hotkey conflict handling. A browser-free target needs a native preferences bridge. Neither migration nor automatic workspace restoration/startup execution is implied by switching UI framework.

## Staged delivery and go/no-go

1. **Baseline/spec lock.** Pin current release binary, OS/WebView2/GPU version, fonts, DPI, theme and physical monitor; capture appearance, focus/a11y and interaction recordings for every surface; enumerate Tauri APIs/window policies and storage keys. Record the `docs/plans/performance-regression/01-release-baseline-and-budgets.md` harness state: its cold-idle runs exist per plan index but complex/manual scenario release measurements remain incomplete [L12].
2. **Host proof before port.** Separately prototype Tauri-free Dioxus host with top/bottom placeholder HWNDs, primary-monitor AppBar register/unregister/recovery, nonactivating transparent popup, DPI and focus/Alt+Tab, fullscreen and Explorer coexistence, shutdown/crash recovery; do **not** run live shell proof without explicit human consent. If native no-WebView is required, separately prove iced/Blitz or another renderer against these same host constraints.
3. **One low-risk presentation slice.** Port a bounded settings/calendar/commands subset and shared theme tokens into isolated Rust/UI code. Verify per-component code, licenses, keyboard/a11y and CSS build. Wire a typed transport to a mock host; verify equivalent state and storage behavior, not just screenshot similarity.
4. **High-risk integration slices.** Tackle bars/task preview/gallery and DWM next; then Stack/OLE/editor, terminal/ConPTY/xterm, speech/WebGL and snipping. Each slice has UI golden/screenshots at fixed DPI/themes, interaction/keyboard/a11y, host IPC/replay/security and focused native failure/rollback tests. Preserve old shell build for A/B parity on the same hardware; no simultaneous live AppBar ownership.
5. **Cutover or abort.** Re-run existing Node/Rust contracts whose logic survives, migrate affected Svelte component tests to new rendered component/bridge tests, add host integration tests plus consented native Windows shell smoke and real Explorer/OLE/DWM/ConPTY/snipping journeys. Cut over only on measured gates and documented regression closure; rollback switches executable/config/profile atomically to original without making current settings unreadable. Do not silently remove Tauri capabilities before the new native ACL is enforced.

**Proposed acceptance gates, not observed facts:** (i) all current user-visible journeys function in primary-monitor scope with equivalent state/error behavior and no lost native authorization; (ii) zero unreviewed AppBar/work-area residue after start, normal exit, crash/relaunch and failed startup in consented tests; (iii) agreed screenshot perceptual diffs/manual visual review and keyboard/screen-reader/mixed-DPI audits close discrepancies, including reduced motion; (iv) on identical release workloads, no material regression in memory growth, input p95, frame pacing, cold/warm startup or CPU versus baseline, with a separately agreed *measured* target if memory savings are the reason to migrate. Define numeric budgets from reliable baseline before declaring success, not retrospectively.

## Memory and speed: hypothesis, not a benchmark

- Tauri's Rust host overhead might disappear in B, but Dioxus desktop brings its own Rust runtime, bridge, webview, CSS, DOM and process tree; moving authored logic from JS to Rust does **not** imply each WebView2 subprocess disappears. More windows/context isolation, CSS and IPC marshaling may offset gains. Existing `App.svelte` lazily loads per-surface UI; measure whether a proposed host preserves that property [L4].
- In D, removing webviews could lower their process/private-byte footprint, but GPU renderer, glyph/cache surfaces, native editor/terminal substitutes, speech model, DWM thumbnails and ConPTY still consume memory; compare *total application process tree* and attributable GPU memory, not main-process RSS alone. Shared WebView2 system processes and page sharing make sums of working sets misleading.
- Webview-to-native event count, OS/window scheduling, image serialization, thumbnail capture, PTY throughput, cold font/shader setup and storage profiles can dominate perceived latency. Native composition may help a specific hotspot or regress typography/IME/a11y; framework labels alone cannot prove p50/p95 improvements.
- Existing `docs/plans/performance-regression/03-native-cache-and-memory-bounds.md` mentions an **uncaptured dev diagnostic** (~19 processes, 1.58 GB working set/1.22 GB private bytes) and explicitly says it is **not evidence**; it includes Vite. Do not use these numbers as a release baseline or promise percentages. The Plan 01 index reports 3 cold-idle release runs but 18 interactive/manual scenario runs blocked [L12]. No target Dioxus or iced benchmark was performed here.

**Reproducible comparison protocol (requires permission for live shell):** use the *same* Windows installation, display topology/DPI, WebView2/driver versions and hardware; build release/packaged variants and use the same model/cache data and window workload. Run >=3 clean repetitions per scenario (increase for noisy distributions), randomize order, report confidence/spread and outliers. Scenarios: cold start to both AppBars ready; warm restart; bars-only idle; every hidden/visible surface; gallery with live/captured DWM; terminal create/replay/heavy output; Stack large folder/editor, search, speech indicator, snipping; 10-minute open/close churn and post-close recovery. Capture per-process PID/tree identity, role and lifetime including WebView2 children and shared system processes; private bytes, working set **with shared-page caveat**, commit, handles/threads, native heap if possible, GPU dedicated/shared allocations and pressure, model allocations, CPU/wakeups and IO. Measure p50/p95 action-to-visible and keyboard-to-result latency, p50/p95/p99 frame timing/long frames, cold/warm readiness and idle CPU. Log request IDs and timestamps through IPC, DOM/native present and DWM paths to attribute deltas; compare same-time screen capture and accessibility trees. Avoid counting a shared process twice; keep release artifacts and test fixture hashes. A reduction in main-process RSS without lower total private bytes or a passed parity gate is **not** a migration win.

## Effort and risk

**Planning ranges only:** assuming two experienced Rust/Windows engineers plus one dedicated frontend/UI engineer with QA/design support, no newly required multi-monitor or workspace features, reusable native service logic, and stable chosen toolchain: **2–4 weeks** inventory/release baseline + isolated host/AppBar/UI spike; **3–6 months** for Tauri-free Dioxus/WebView2 parity candidate with editor/terminal preserved if the host spike passes; **6–12+ months** for browser-free native parity candidate, strongly dependent on editor/terminal/graphics replacements and HWND event-loop feasibility. Calendar time includes consented Windows regression work and migration; estimates are not productivity benchmarks or delivery commitments. One engineer, missing OS integration hooks, incompatible components or strict pixel-perfect/screen-reader parity can exceed these ranges substantially. The quickest plausible way to realize targeted performance gains is likely profiling current stack first, not rewriting everything.

| Risk | Why it matters / mitigation |
|---|---|
| Host cannot safely expose/manage HWNDs and Windows main-thread OLE | Prototype window/event-loop/AppBar/drag first; preserve old executable, native rollback and Explorer state. |
| Security regression via broad replacement IPC | Typed least-privilege caller/instance authorization; adversarial tests for stale nonce, wrong label, malformed payload, renderer-supplied paths/handles. |
| Editor, terminal and orb incompatibility | Dioxus desktop prototype actual xterm/CodeMirror/WebGL. Browser-free path budgets replacements and conformance tests rather than substituting text controls. |
| CSS and visual parity drift | Adapt copied components to JasonShell tokens; baseline screenshots, DPI/font/contrast/reduced-motion and interaction reviews, not stock demos. |
| Increased memory or regressions in multi-webview startup | Release A/B measurement per actual window lifetime, shared process attribution, no savings claim before evidence. |
| Storage split / broken updates | Enumerate data ownership; reversible migration, idempotent imports and rollback to old binary/profile. |
| Upstream/API/license surprises | Pin Rust/UI components and Dioxus host version; inspect exact component source/license/assets/dependencies; treat experimental native renderer as research only. |

**Decisions still needed:** Is “remove Tauri” the only hard host constraint, or is *no WebView2/no JS* required? Is full parity literal pixel/behavior/accessibility equivalence or a negotiated acceptance threshold? What memory metric and release workload matter most? Is human consent available for live AppBar/OLE/DWM/snip benchmarks? Which runtime versions, CSS/JS bundles and copied component revisions are approved after prototype verification?

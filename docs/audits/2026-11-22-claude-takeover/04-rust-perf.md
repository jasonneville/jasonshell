## Rust performance, concurrency & code health audit

Scope: `src-tauri/src` (153 `.rs` files, 89,521 lines including inline tests), `src-tauri/Cargo.toml`, `src-tauri/build.rs`, `src-tauri/tests`, `src-tauri/examples`. Read-only. No app run. `docs/` and root plan/audit `.md` files were not read. IPC/serialization contracts and Win32 unsafe/security correctness belong to other lanes; where a finding crosses those lanes it is flagged "cross-lane" and kept short.

Method: grep counts (split production vs. inline-test code with a brace-tracking heuristic: `#[cfg(test)] mod … {}` blocks, `tests.rs`, `*_harness.rs`, and `text_document/feasibility/**` count as test), then targeted reads of the hot paths. Every evidence pointer below was opened and read. Line numbers are from the current dirty worktree.

Threading model summary: Tauri 2 on tao/wry. The main (UI/event-loop) thread runs every synchronous `#[tauri::command]`, every `on_window_event` callback, and `setup`. Async commands run on Tauri's tokio runtime, and most native work is pushed to `tauri::async_runtime::spawn_blocking` (the tokio blocking pool, max 512 threads). Alongside that, about 33 ad-hoc `std::thread` sites create long-lived or per-operation OS threads: the taskbar snapshot worker, notification poller, fullscreen guard (4 Hz), legacy taskbar guard (10 Hz), System Info scheduler (20 Hz), folder-watch workers, PTY readers (one per stream), git/process drains (two per child), quick-command waiters (three per run), the speech capture, health, meter and limit workers, the keyboard hook and hotkey message-loop threads, and the clipboard STA thread. No pool or executor is shared across subsystems, and lifecycle code is mostly hand-rolled `AtomicBool` stop flags plus `is_finished()` and `sleep(10ms)` reaping.

### Findings

#### A. Threading model & main-thread blocking

- **RS-01: About 147 synchronous Tauri commands run on the UI thread, and several do blocking I/O** (Critical, M). Evidence: `src-tauri/src/stack_popup.rs:393` `read_stack_folder` (sync `fn`): it does a full `read_dir`, a `fs::metadata` per entry, a sort and a per-page `symlink_metadata`. Also `stack_popup.rs:1452` `suggest_stack_paths` (`read_dir` plus `is_dir()` per entry), `stack_popup.rs:1605` `copy_stack_items` (`canonicalize` per path plus OLE clipboard), `dev_tools/git_status.rs:23` `get_workspace_git_status` (spawns `git` twice with `Command::output()` and no timeout), `system_tray.rs:108` `list_system_tray_icons` (cross-process `SendMessageTimeoutW`/`ReadProcessMemory` plus PNG encode per icon), `launchers.rs:13` `list_pinned_taskbar_apps` (COM `.lnk` resolution plus icon extraction), `audio.rs:68-140` (all 12 audio commands are sync), and `settings.rs:385-457` (disk read/parse/write). In Tauri 2, commands not declared `async` run on the main thread, so the event loop stalls for every window: top bar, bottom bar and all popups. A slow network share, a cold disk, a hung Explorer tray or a large repo freezes the whole shell. Problem: no rule says which commands may touch I/O. Recommendation: make every command that touches the filesystem, COM, child processes or another process `async` (or `#[tauri::command(async)]`) and route it through one `run_blocking(…)` helper on the tokio blocking pool (see RS-37). Keep sync commands only for pure in-memory reads and window-geometry calls that must be on the main thread. Add a CI test that parses `generate_handler!` (build.rs already does this, see `build.rs:16-31`) and fails when a sync command calls `std::fs`, `Command` or `CoCreateInstance`.

- **RS-02: `COMMAND_PANEL` resize does a full settings read-validate-write on every `Resized` event, on the main thread** (High, S). Evidence: `main.rs:623-630` calls `command_panel::save_command_panel_size_for_app` for each `WindowEvent::Resized`. `command_panel.rs:124-142` then calls `settings::update_shell_settings_for_app`. That runs `load_settings_from_path` (`settings.rs:748-773`: `read_to_string`, parse to `Value`, migrate, `to_value` again for the secret scan, validate), then `missing_hotkeys_at` reads and parses the file a second time (`settings.rs:73-76`, `:775-779`), then `to_vec_pretty` and `write_file_atomic` (`settings.rs:1361-1365`). An interactive drag fires dozens to hundreds of `Resized` events per second, so each drag does hundreds of file read/parse/write cycles on the UI thread. Recommendation: keep the latest size in memory and persist once, trailing-debounced (about 500 ms after the last resize, or on `Moved/Resized` end/blur/hide), on a background worker. With an in-memory settings cache (RS-26), the write becomes a single serialize.

- **RS-03: `spawn_blocking` with `thread::sleep(150ms)` used as a timer** (Medium, S). Evidence: `main.rs:475-478` and `main.rs:585-589`. Every focus-loss of Settings, Process Manager or Command panel parks a tokio blocking-pool thread for 150 ms just to sleep. Recommendation: use `tokio::time::sleep` (Tauri's runtime is tokio; enable the `time` feature on a direct `tokio` dependency with the same version Tauri uses), or a single timer thread or timer wheel. This frees pool threads and makes the delay cancellable when the generation changes.

- **RS-04: Startup `setup` sleeps on the main thread for at least 400 ms and up to about 4 s** (High, M). Evidence: `appbar.rs:161-166` (`WORK_AREA_RETRY_ATTEMPTS = 20`, `WORK_AREA_RETRY_DELAY = 50ms`, `STARTUP_STABILIZATION_DELAY = 100ms`, `STARTUP_STABILIZATION_POLLS = 15`, `REQUIRED_STABLE_POLLS = 3`). `appbar.rs:1261-1302` (`stabilize_runtime_window_rect_with`) sleeps 100 ms per poll and needs 3 stable polls. It is called twice (top and bottom) from `activate_shell_surfaces` (`appbar.rs:756-770`), which runs inside `.setup` (`main.rs:685`). `set_work_area_with_retry` (`appbar.rs:1045-1056`) adds up to 20×50 ms. The same stabilizer is reused on the restore path (`appbar.rs:1886-1895`). While the main thread sleeps, no webview can paint and no IPC is serviced. Recommendation: run stabilization as a state machine driven by `SetTimer`/`WM_TIMER` or `run_on_main_thread` re-posts instead of sleeping. Better, react to `WM_WINDOWPOSCHANGED` and the AppBar `ABN_POSCHANGED` notification rather than polling the rect. Polls on both bars can at least run in parallel.

- **RS-05: System Info scheduler wakes at 20 Hz for the whole app lifetime and makes two synchronous main-thread round-trips per tick** (High, S). Evidence: `process_manager/native_runtime.rs:62-100`: `loop { sleep(50ms); … window.is_visible(); window.is_focused(); … }`. The loop exits only when the `process-manager` window is destroyed or `stop` is set, not when the panel is hidden. On tao/wry, `is_visible`/`is_focused` are dispatched to the event loop and the caller waits for the reply, so this costs about 40 cross-thread UI round-trips per second even with the panel hidden. It also polls `workers` via `is_finished()` 20 times per second. Recommendation: drive the scheduler from window events, since `on_window_event` already sees `Focused`/`Destroyed` (`main.rs:396-473`). Park the thread on a `Condvar`/channel while hidden. Use `recv_timeout(next_lane_due)` instead of a fixed 50 ms tick.

- **RS-06: Polling loops where an OS notification exists** (Medium, M). Evidence: fullscreen guard `appbar.rs:1602-1622` polls `foreground_fullscreen_target_for_layout_with_state` every 250 ms (`FULLSCREEN_GUARD_POLL_DELAY`). The legacy Explorer taskbar guard `appbar.rs:2074-2082` locks a mutex and reconciles every 100 ms. The taskbar snapshot runs a full scan every 1 s even without signals (`task_windows/windows.rs:43`, `:136-174`). The notification listener polls every 1 s (`task_windows/notifications.rs:11`). Speech capture health polls every 10 ms (`speech_runtime.rs:1533-1536`), the meter every 50 ms (`:1584-1587`), and the speech clipboard pump every 10 ms (`speech_clipboard.rs:61`). Each is a permanent wakeup source that keeps the CPU out of deep C-states, which matters for a shell that is always running. Recommendation: for fullscreen, use the `ABN_FULLSCREENAPP` AppBar callback (the shell is already an AppBar) or `SetWinEventHook(EVENT_SYSTEM_FOREGROUND | EVENT_OBJECT_LOCATIONCHANGE)`. Explorer's taskbar has the v2 event-driven path (`appbar.rs:2095-2110`, `explorer::wait_for_taskbar_reconcile`), so retire the 100 ms legacy guard. For taskbar windows, rely on the WinEvent/shell-hook signals already plumbed through `TaskbarRefreshReason::Native` and stretch the safety-net cadence to 5-10 s. For notifications, use `UserNotificationListener::NotificationChanged` where it is available (packaged identity) and otherwise back off when nothing changes.

- **RS-07: Five hand-written child supervisors use `try_wait()` plus sleep polling, and a 50 ms poll sets a latency floor on every git call** (High, M). Evidence: `stack_popup/process_runner.rs:372-405` (`wait_with_deadline` sleeps `poll_interval`), with `poll_interval: Duration::from_millis(50)` at `stack_popup/git_status.rs:1653` and `stack_popup.rs:2533`. Others: `process_manager/probe_executor.rs:111-195` (PeekNamedPipe plus 10 ms sleep), `snipping/composition.rs:12-38`, `snipping/clipboard_process.rs:130-191`, `stack_popup/terminal.rs:779-800`. Each child also gets two drain threads (`process_runner.rs:405-430`, `spawn_drain`, 4 KiB stack buffers). A `git rev-parse` that finishes in 8 ms is reported after 50 ms. The Stack git refresh chain (RS-12) runs 6-8 git processes sequentially, so it pays at least 300-400 ms of pure polling latency, plus 12-16 thread creations. Recommendation: wait on the process handle with `WaitForSingleObject(handle, remaining_ms)` (or `WaitForMultipleObjects` on process plus cancel event). This gives exit latency of a few microseconds and needs no polling. Read stdout/stderr either with one overlapped-I/O thread or by reading stderr on the calling thread after stdout EOF. Collapse the five supervisors into one `ChildSupervisor` (job object, deadline, caps, kill-tree), which the codebase already half-has in `process_runner` and `probe_executor`.

- **RS-08: Ad-hoc thread-per-operation for COM work, with the caller blocking on `join()`** (Medium, S). Evidence: `audio.rs:379-399` `run_in_mta` spawns a new OS thread, runs `CoInitializeEx(MTA)` and builds the device enumerator, then `CoUninitialize` and `join()`, for every audio command including `set_master_volume`/`set_app_volume` during slider drags. `launchers.rs:516-537` `run_in_sta` does the same for STA. The caller is a sync command (RS-01), so the UI thread still blocks for thread creation, COM init and the operation. Recommendation: create one long-lived MTA "audio service" thread that owns a cached `IMMDeviceEnumerator`/`IAudioEndpointVolume`, takes requests over a channel, and coalesces slider updates (only the latest value matters). Do the same with a single STA worker for shell/COM link work, reused by `search/providers/apps.rs:694-741` (which currently runs `CoInitializeEx`/`CoUninitialize` per shortcut).

- **RS-09: No shared executor; threads are unnamed and reaped by polling** (Medium, M). Evidence: 33 production spawn sites (largest: `speech_runtime.rs` 11, `appbar.rs` 4, `quick_commands.rs` 4, `quick_command_notification.rs` 4, `windows_key_hook.rs` 4, `process_runner.rs` 4). Only about 10 call `Builder::name` (`graceful_exit.rs:88`, `quick_command_notification.rs:192/474`, `folder_watch/native.rs:73`, `windows_key_hook.rs:283/1098`, `speech_clipboard.rs:318`, snipping pipes). `shutdown_workers.rs:12-50` (`WorkerGroup`) is a good admission/drain abstraction, but it has only 10 users and reaps with `is_finished()` plus `sleep(10ms)` (`shutdown_workers.rs:33-48`). Problem: crash dumps and ETW traces show anonymous threads, and every subsystem reinvents start, stop and drain. Recommendation: standardize on `WorkerGroup::spawn_named(name, f)` and require names. Replace the `is_finished`/sleep drains with a completion `Condvar` or a counted `std::sync::Barrier`-style latch. Consider tokio `JoinSet` plus `CancellationToken` (tokio-util) for the many "worker with generation and stop flag" patterns.

- **RS-10: `StackPopupRuntimeState` is one global mutex shared by clipboard, drag/drop, focus holds, undo and all terminal sessions** (Medium, M). Evidence: `stack_popup/models.rs:5-25` (single struct). 73 sites take `State<'_, Mutex<StackPopupRuntimeState>>`. Terminal read/write/resize/poll, clipboard set, drag and focus-hold code all serialize on it (`stack_popup/terminal.rs:396-441, 465-493, 532-548`, `stack_popup/clipboard.rs:175`). Terminal polling (`poll_stack_terminal_session`, sync, on the UI thread) also calls `reap_finished_terminal_drains`, which clones every draining slot under the lock (`terminal.rs:709-723`). Recommendation: split it into independent state objects managed by Tauri: `TerminalRegistry` (its own `Mutex` or `DashMap<SessionId, Arc<Session>>`), `ClipboardState` and `DragDropState`. Use `parking_lot::Mutex` (no poisoning, smaller, faster uncontended).

- **RS-11: Locks held across IPC emits and other slow calls** (Medium, S). Evidence: `stack_popup/folder_watch.rs:291-305` holds `runtime.registry.lock()` across `destination.emit_to(...)`; `:315-331` does the same for the error path. In `task_windows/windows.rs:350-370` the snapshot is cloned into `LAST_TASKBAR_SNAPSHOT` and then emitted (not under the lock, which is fine), but `TASKBAR_REFRESH_DIAGNOSTICS` is locked four times per cycle. `quick_commands.rs:1285-1355` runs ANSI decode and transcript cloning inside the global `RUNS` lock that both stdout and stderr reader threads contend on. Recommendation: under the lock, only check the generation and copy the payload; emit after dropping the guard. A generation check is still valid after dropping the lock if the frontend ignores stale `watch_id`s, which it must already do for out-of-order events.

- **RS-12: Mixed poison policies** (Low, S). Evidence: `stack_popup/paging.rs:600-606` uses `.expect("…poisoned")`, which panics. `stack_popup/terminal.rs:378` uses `unwrap_or_else(|poison| poison.into_inner())`, which recovers. Most other sites map to a `String` error (`"Failed to lock stack popup runtime state"`), which permanently fails that feature after one panic. Counts: 53 `lock().unwrap/expect`, 11 `into_inner`, the rest `map_err`. Recommendation: pick one policy. For a shell that must stay up, `parking_lot::Mutex` (no poisoning) plus `catch_unwind` at worker boundaries is the simplest. Otherwise, add a crate-wide `lock_or_recover()` extension trait.

#### B. Process spawning (git, PowerShell, self-exe helpers)

- **RS-13: The Stack git status refresh spawns 6-8 sequential `git.exe` processes** (High, M). Evidence: `stack_popup/git_status.rs:296-347` runs `rev-parse --show-toplevel`, `branch --show-current`, `status --porcelain=v1 -z --untracked-files=all`, `diff --cached --numstat -z`, `diff --numstat -z`, then `git_remote_repository_url` (up to two `config --get`, `:395-411`/`:1975`) and `git_ahead_behind` (`rev-list --left-right --count`, `:349-362`). The summary and metadata variants (`:262-294`) add more `rev-parse` and `for-each-ref` calls. Each process costs a Windows process creation (~10-30 ms for git.exe with its MSYS DLLs), two drain threads and the 50 ms poll floor (RS-07). It is triggered on every folder-watch change, after a 200 ms debounce (`folder_watch/native.rs:25`). Recommendation, cheapest first:
  1. Use `git status --porcelain=v2 --branch -z --untracked-files=all` (already used in `dev_tools/git_status.rs:28-34`). It returns branch, upstream and ahead/behind in one call, which removes `branch --show-current`, `rev-list` and `for-each-ref`.
  2. Run the two `diff --numstat` calls in parallel with `status`, or skip them when the UI does not show line stats.
  3. Cache `rev-parse --show-toplevel/--absolute-git-dir/--git-common-dir` and the `remote.*.url` config per repository root, keyed on the mtimes of `.git/HEAD` and `.git/config`.
  4. Bigger step: add `gix` (gitoxide) for read-only paths (discover, HEAD/branch, config, ahead/behind via the rev-walk). `gix::status` is maturing; keep git.exe for status and all mutations. Trade-off: about 2-4 MB of binary and compile time, but zero process spawns for metadata. `git2` (libgit2) is an alternative with a C dependency and slower status on large repos than git.exe with fsmonitor.

- **RS-14: git `stdout_cap` of 64 KiB silently truncates `status` on medium repos** (High, S, correctness with perf implications). Evidence: `stack_popup/git_status.rs:1648-1649` (`stdout_cap: 64 * 1024`). `git_stdout_bytes` (`:1572-1578`) returns `output.stdout` without checking `stdout_truncated`, which is checked only in the metadata paths (`:375-383`). `status --porcelain=v1 -z --untracked-files=all` emits path plus NUL per change; 64 KiB is roughly 1,000-1,500 changed or untracked paths (for example an un-ignored build directory). The status is then parsed from a truncated NUL stream. Recommendation: raise the cap for `status` (for example 8 MiB) and treat truncation as an explicit "too many changes" state. Or stream-parse the records and stop at N rows while still reporting the total count.

- **RS-15: `trusted_git_path()` stats up to four candidate paths for every git invocation** (Low, S). Evidence: `stack_popup/git_status.rs:1669-1692` (`git_candidates` plus `is_file()`), called from `run_git_command` (`:1640-1644`) and again from `stack_git_watch_roots` (`:248-252`). Recommendation: cache it in a `OnceLock<Result<PathBuf, String>>`, or with a short TTL if users may install Git while the shell runs.

- **RS-16: `process_runner` (git, taskkill and other children) does not pass `CREATE_NO_WINDOW`** (Medium, S, cross-lane note). Evidence: `stack_popup/process_runner.rs:71-96` sets no `creation_flags`; only `probe_executor.rs:111` and `quick_commands/windows_launch.rs:244/312` do. `main.rs` has no `windows_subsystem = "windows"` attribute (grep found none in `src-tauri/src`). The release binary is therefore console-subsystem, and console children inherit the parent's console today, so nothing flashes. If the subsystem is ever switched to GUI (expected for a shell), every git and taskkill spawn will flash a console window and pay conhost creation (about 5-15 ms each). Recommendation: set `CREATE_NO_WINDOW` in `run_process` unconditionally, and decide on the subsystem explicitly (the Win32 lane owns that call).

- **RS-17: A second, divergent git layer in `dev_tools/git_status.rs`** (Medium, S). Evidence: `dev_tools/git_status.rs:23-58` and `:170-180` call `Command::new("git")`. That is PATH-resolved, unlike `trusted_git_path`, and runs `.output()` with no timeout, no output cap, no kill-tree and no `GIT_OPTIONAL_LOCKS=0`, inside a sync command on the UI thread (RS-01). Recommendation: delete this layer or route it through `stack_popup::git_status::run_git_command`. Keep one git module (`git/` with `runner.rs`, `parse.rs`, `ops.rs`).

- **RS-18: The System Info volume probe spawns the 49.8 MB shell executable once per volume, sequentially** (High, M). Evidence: `process_manager/volume_probe.rs:120-160` runs `current_exe()` with `--internal-system-info-volume <root>`, a 1,500 ms deadline, up to 32 roots, one after another. The Storage lane repeats every 15 s while visible (`process_manager/system_info.rs:34-40`). `target/release/jason-shell.exe` is 49.8 MB because ORT and tokenizers are statically linked. Each helper start maps that image and runs the full CRT/static-init path, then walks the helper-arg dispatch in `main.rs:100-123`. Isolation from hung network drives is the right goal, but the vehicle is heavy. Recommendation: add a tiny dedicated helper bin (precedent: `src/bin/snip-clipboard-owner.rs` builds to 359 KB) or keep one long-lived probe child that serves all roots over a pipe. Run local fixed volumes in-process (`GetDiskFreeSpaceExW` on `DRIVE_FIXED` cannot hang the way `DRIVE_REMOTE` can) and isolate only remote or removable roots, in parallel with a shared deadline.

- **RS-19: Other self-exe and PowerShell spawns on interactive paths** (Medium, S). Evidence: `snipping/composition.rs:24-25` spawns `current_exe --internal-snip-composition-flush` per snip flush. `snipping/native.rs:207` and `quick_commands/windows_launch.rs:277/368` also self-spawn. `launchers.rs:502-511` `copy_text_to_clipboard` spawns `powershell.exe -NoProfile -Command Set-Clipboard` (PowerShell cold start is about 200-600 ms) even though native clipboard code already exists (`speech_clipboard.rs`, `stack_popup/clipboard.rs`, `snipping/clipboard.rs`). Recommendation: put all `--internal-*` helper modes in one small helper binary without ORT/WebView2 linkage, and replace the PowerShell clipboard with the existing native `CF_UNICODETEXT` path.

#### C. Filesystem hot paths (Stack browser)

- **RS-20: Folder listing calls `fs::metadata(path)` per entry instead of the free `DirEntry::metadata()`** (High, S). Evidence: `stack_popup/paging.rs:609-642` `stack_folder_entry_summary` calls `fs::metadata(&path)` for `modified_at` (`:637-639`, and for symlinks `:621-624`), even though `entry.file_type()` is already used. On Windows, `std::fs::DirEntry::metadata()` comes from the `FindNextFileW` data at no extra cost. `fs::metadata(path)` opens a handle per file (`CreateFileW` plus `GetFileInformationByHandle` plus `CloseHandle`), roughly 20-100 µs locally, milliseconds on SMB, and it triggers AV filter callbacks. With `MAX_FILESYSTEM_LISTING_ENTRIES = 10_000` (`:14`), opening a large Downloads folder costs up to 10k extra handle opens before page 1 appears. The page then calls `stack_item_metadata_from_path` (`paging.rs:93-101` → `items.rs:18-26`), which does `symlink_metadata` plus a possible `metadata` again for the 80 visible rows. Recommendation: use `entry.metadata()` (for non-reparse entries it equals `symlink_metadata`) and carry the `Metadata` (or the fields you need) in `StackFolderEntrySummary` so the page build does not stat again. For very large folders, consider `GetFileInformationByHandleEx(FileIdBothDirectoryInfo)` batch enumeration.

- **RS-21: The sort comparator allocates two lowercase `String`s per comparison** (Medium, S). Evidence: `stack_popup/paging.rs:269-295`. `compare_stack_entries`/`compare_newest_first` call `a.name.to_lowercase().cmp(&b.name.to_lowercase())`, and `paging.rs:180` uses `sort_by`. For n = 10,000 that is about 2·n·log₂n ≈ 270k String allocations plus Unicode case mapping per folder open. The same pattern is in `stack_popup.rs:1478` (`suggest_stack_paths`), `finalize_zip_children` (`paging.rs:428`) and the apps index (`search/providers/apps.rs:381`). Recommendation: precompute a `sort_key: Box<str>` (lowercased once) in the summary, or use `sort_by_cached_key`. Better for Explorer parity: compare with `CompareStringOrdinal(…, bIgnoreCase=TRUE)` or a natural-sort key (`StrCmpLogicalW` semantics) computed once.

- **RS-22: The session-store budget is recomputed in O(sessions × entries) inside a loop** (Low, S). Evidence: `stack_popup/paging.rs:560-595`. `enforce_session_budget` loops, and each iteration sums `entries.len()` and `estimated_bytes()` over all sessions; `estimated_bytes` walks every entry (`:644-659`). With 32 sessions × 10k entries that is up to 320k entry visits per eviction step. Recommendation: keep running totals (`total_entries`, `total_bytes`) updated on insert and remove.

- **RS-23: An unconditional `eprintln!` with the full path on every folder page** (Low, S). Evidence: `stack_popup/paging.rs:184-206`. Every page read writes a roughly 250-byte line to stderr. Stderr on a console-subsystem process is a synchronous conhost write that takes the global stderr lock. It also leaks user paths into whatever captures stderr. Recommendation: put this behind `tracing::debug!` (RS-44), or a `cfg(debug_assertions)` or env-gated flag.

- **RS-24: A paste/copy walks the source tree four times and emits a broadcast event per file** (Medium, M). Evidence: `stack_popup/clipboard.rs:375-381` runs `scan_copy_totals` (`file_ops.rs:715`). #### D. Icons, images & payload encoding

- **RS-25: `BoundedStringCache` is O(n) per get and insert; four separate caches duplicate the same icon work** (High, S). Evidence: `task_windows/bounded_string_cache.rs:32-78`. `get_cloned` runs `evict_expired()`, which scans the whole `order` VecDeque and allocates a `Vec<K>` of expired keys on every lookup. `touch` and `insert_internal` do `order.retain(...)`, which is O(n). - **RS-26: Icons and previews travel as base64 PNG data URLs inside JSON** (High, L, cross-lane note). - **RS-27: Window preview captures full resolution, then nearest-neighbour downscales and PNG-encodes at default compression** (Medium, S). Evidence: `task_windows/previews.rs:66-105` captures at window size. `:354-379` `scale_rgba` is a per-pixel float nearest-neighbour loop (aliasing, and a full-size buffer allocated first). `:381-396` encodes with `png::Encoder` at default compression and adaptive filters, then base64-encodes. - **RS-28: Saved snips are written as uncompressed ("stored") PNGs** (Medium, S). Evidence: `snipping/coordinator.rs:462-475` `save` uses `super::clipboard::png_rgba(...)`, which is `snipping/clipboard.rs:205-219`, and `encode_rgba` (`:148-190`) writes zlib stored blocks ("filter 0, zlib stored blocks", `:144-145`). - **RS-29: The stack icon cache is keyed per file path, not per icon identity** (Medium, S). Evidence: `stack_popup/icons.rs:81-101` and `:137-140` (key = lowercased full path), capacity 128 (`:13`). - **RS-30: The process list ships one icon data URL per process every refresh, through a cache smaller than the working set** (Medium, S). - **RS-31: The taskbar snapshot does expensive per-window work for every top-level window before cheap filters, and sends the full snapshot every second** (High, M). #### E. IPC event fan-out (internal cost side)

- **RS-32: `emit` (broadcast) used for high-volume events in a 20-webview app** (High, S). Evidence: 24 production `.emit(` sites. High-volume ones: `search/mod.rs:84-87` (every search progress payload, three or four per keystroke), `task_windows/windows.rs:365` (taskbar snapshot, 1 Hz), `dev_tools/task_runner.rs:297` (every 4 KiB of task output), `stack_popup/clipboard.rs:192/360` and `stack_popup.rs:2004/2051/2490` (file-operation progress per file), `search/providers/apps.rs:241`, `speech_runtime.rs:1765`. There are 21 capability files in `src-tauri/capabilities/` (one per surface), so every broadcast is serialized once and delivered and evaluated in about 20 webviews, most of which have no listener. Recommendation: use `emit_to(EventTarget::webview_window(label), …)` everywhere. For streams such as search progress and task output, use `tauri::ipc::Channel<T>` passed in by the invoking webview; it is point-to-point and ordered.

- **RS-33: Terminal output is emitted per 4 KiB read with no coalescing, and every byte is also buffered in an unbounded-in-practice second path** (High, M). Evidence: `stack_popup/terminal.rs:961-1031`. The PTY reader thread does a 4 KiB `read`, decodes, builds `StackTerminalOutputChunk` (cloning `session_id`), calls `emit_to`, and then also `tx.try_send(...)` into `sync_channel(1024)` (`:904`). If the poll path (`poll_stack_terminal_session`, `:525-560`) is not draining, which is the case when the UI uses events, the channel retains up to 1024 × 4 KiB ≈ 4 MiB per session and then silently drops data (`TrySendError::Full(_) => {}`, `:1003`), so the poll path is lossy too. A `cat` of a large file produces thousands of IPC events per second, each a JSON string with escaping. Recommendation: pick one transport. The usual pattern is a frame-coalescing reader: read into a 64 KiB buffer and flush either when the buffer is full or 8-16 ms after the first unflushed byte (a 60 Hz frame). Deliver through a `Channel<Vec<u8>>`/`ipc::Response` raw bytes (xterm.js accepts `Uint8Array` and does UTF-8 decoding itself), which removes the Rust-side UTF-8 decode (`:1034-1063`, which also double-copies via `valid.to_string()` and `pending[valid_up_to..].to_vec()`). Use the ring buffer only for reattach scrollback, bounded in bytes.

- **RS-34: Every keystroke written to a terminal makes one blocking-pool task, two clones and one extra emit** (Medium, S). Evidence: `stack_popup/terminal.rs:389-444`. It takes the global state lock, clones `request.input` (`:420`), runs `spawn_blocking` for `write_all` and `flush`, takes the state lock again for `observe_terminal_input_for_cwd`, then calls `emit_cwd_update` (`:443`, `:1522-1536`) on every write, even when the cwd did not change. Recommendation: keep a per-session writer thread fed by an `mpsc` channel (writes to a ConPTY pipe are cheap but blocking). Emit a cwd update only when `observe_terminal_input_for_cwd` returns `Some` and differs. Avoid the clone by observing before moving.

- **RS-35: Quick-command output is stored three times per chunk under a global lock, and byte truncation can split UTF-8** (Medium, S). Evidence: `quick_commands.rs:1285-1355` (`append_running_output`) appends `body` to `run.stdout`/`stderr` (bytes), pushes a transcript entry with `body.clone()`, and returns a payload holding `body`. `target.truncate(OUTPUT_LIMIT)` at `:1316` cuts a `Vec<u8>` built from a `String`, so it can split a multi-byte character, and the history entry later converts it lossily. `RUNS` is one `Mutex<HashMap<…>>` (`:73`) shared by all runs and both stream threads (`:906-907`). Each run also spawns three OS threads (waiter plus stdout plus stderr, `:901-907`). Recommendation: keep one source of truth (the transcript, as `Arc<str>` bodies) and derive stdout/stderr views. Truncate on a char boundary (`floor_char_boundary` on nightly; for stable, a `str::is_char_boundary` loop). Use a per-run `Mutex`.

#### G. Speech runtime

- **RS-41: The 652 MB ONNX encoder is loaded eagerly at startup and kept resident forever** (High, M). Evidence: `main.rs:643` `speech_runtime::spawn_warm_model_async(app.handle().clone())` runs first in `setup`. `speech_runtime.rs:475-505` loads it on the blocking pool. `speech_model.rs:36-39` calls `ParakeetTDT::from_pretrained(model_directory, None)`, which uses default ORT session options. `resources/speech-models/parakeet-tdt-0.6b-v2-int8/encoder-model.int8.onnx` is 652,184,014 bytes. Results: roughly 0.7-1.2 GB resident (weights plus ORT arena) for a shell that may never dictate, multi-second CPU contention during boot competing with webview start-up, and default `intra_op` threads, which equal the physical cores and can contend with the UI during transcription. Recommendation: warm lazily, on first use of the speech hotkey or after an idle delay (for example 30 s after the shell is ready, at low thread priority). Unload after N minutes idle (the `model_pool` take/return design in `:450-470` already supports this). Pass explicit ORT options: `with_intra_threads(physical/2)`, `with_memory_pattern(true)`, and `GraphOptimizationLevel::Level3` with `with_optimized_model_path` so the optimized graph is cached on disk and later loads are faster. If parakeet-rs does not expose these, add a small upstream patch. Consider `mmap` model loading (ORT `session.use_device_allocator_for_initializers`, external data) to keep pages file-backed.

- **RS-42: The audio callback allocates and resamples by sample dropping without an anti-alias filter** (Medium, S). Evidence: `speech_runtime.rs:1950-1971`. Inside the real-time cpal callback, `Vec::with_capacity(SEGMENT_SAMPLES)` allocates every 2,560 samples (`speech_streaming.rs:12`) and `into_boxed_slice` hands it off. Allocation in an RT audio callback risks glitches under allocator contention. The phase-accumulator decimation (`phase += TARGET_RATE; while phase >= source_rate { push(mono) }`) keeps every third sample at 48 kHz with no low-pass filter, so 8-24 kHz content aliases into the 0-8 kHz ASR band, which measurably hurts accuracy in noisy rooms. Recommendation: preallocate a pool of segment buffers (a lock-free SPSC ring such as `rtrb` or `ringbuf`, or recycle boxes back through a return channel). Resample off the RT thread with `rubato` (SincFixedIn or FftFixedIn), or at least a simple FIR or biquad low-pass before decimation. `realfft` is already in the dependency tree via parakeet-rs.

- **RS-43: Speech worker supervision uses 2, 10, 25 and 50 ms sleep loops** (Low, S). Evidence: `speech_runtime.rs:1288` (`sleep(2ms)` spin while waiting for `Transcribing`), `:1535` (10 ms health loop that takes `state.commit` lock every tick), `:1586` (50 ms meter), `:1687` (25 ms). Recommendation: use `Condvar` notifications on status transitions and a `recv_timeout` on the meter; a 50 ms meter is fine, but the 2 ms spin and the 10 ms locked health loop are not.

Evidence: 1,031 production `Result<…, String>` signatures, 1,106 `.to_string()`, 873 `format!`, and many `map_err(|error| format!("Failed to …: {error}"))` chains (for example `stack_popup/paging.rs:158`, `git_status.rs:1567-1700`). `git_status.rs:56-82` already reinvents a typed enum (`GitCommandError`) and immediately flattens it with `into_message`. Costs: allocation on every error path (including expected ones such as "not a repo"), no programmatic matching (callers compare strings, for example `MissingConfig` detection by exact args at `git_status.rs:1656-1666`), and no `source()` chain for diagnostics. Recommendation: use `thiserror` enums per subsystem (`GitError`, `FsError`, `SettingsError`) with `#[from] io::Error`. Implement `serde::Serialize` (or `Into<tauri::ipc::InvokeError>`) once at the command boundary so the IPC contract stays string-shaped. Use `anyhow` only for top-level glue if wanted.

- **RS-50: Tests that assert on production source text** (Medium, M). Evidence: 28 `include_str!(…)`/`read_to_string(file!())` sites in 12 files. Examples: `quick_commands.rs:1990-2033` (`quick_commands_production_source()`, `source[mark..].find("&stopping_snapshot,")`), `process_manager.rs:1516-1536` (asserts the handler text contains `"callers: &[PROCESS_MANAGER_LABEL]"`), `stack_popup/process_runner.rs:771-773` (asserts `wait_with_deadline` source contains `child.try_wait()`), `stack_popup.rs:3745`, `command_panel.rs:361`, `settings.rs:1414/1437`, `launchers.rs:1106`. These tests lock in implementation details. For example, RS-07's fix (replace `try_wait` polling with `WaitForSingleObject`) would fail `process_runner.rs:772-773` even though behaviour improves. Problem: refactors for performance become test churn, which discourages exactly the changes in this audit. Recommendation: replace source-text assertions with behavioural tests (inject the runner, observe ordering through a recorder, as `refresh_acceptance::record_command` already does in `git_status.rs:1627`). For true structural invariants, such as "every command authorizes the caller", use a proc-macro or attribute (`#[authorized(callers = [...])]`) that the compiler enforces.

- **RS-51: No logging or tracing framework, and no runtime observability beyond ad-hoc structs** (Medium, M). Evidence: zero `log::`/`tracing::` uses. 48 production `eprintln!` calls (for example `paging.rs:191`, `appbar.rs:1287`, `appbar.rs:1624-1628`, `main.rs:104/689`). `diagnostics.rs` is a 200-entry in-memory ring fed from the frontend. Hand-rolled timing structs are `StackFolderPageDiagnostics` (`paging.rs:112-122`), `SearchProviderTiming` (`search/mod.rs:189-199`), `TaskbarRefreshDiagnostics` (`task_windows/windows.rs:150-183`) and `FULLSCREEN_GUARD_WAKE_COUNT` (`appbar.rs:1598`). Recommendation: add `tracing` plus `tracing-subscriber` with an `EnvFilter` (`JASONSHELL_LOG=jason_shell::stack_popup=debug`) and a rolling file appender (`tracing-appender`). Instrument the hot paths with `#[instrument(skip_all, fields(...))]`: git runs, folder page, search phases, icon extraction, taskbar scan, speech transcribe. Add `tracing-chrome` or `tracing-tracy` behind a feature flag for timeline profiling. The existing diagnostics structs can become span fields, so the IPC-visible diagnostics stay.

- **RS-52: No benchmarks** (Medium, M). Evidence: no `benches/` directory, no `criterion`/`divan` dependency, and no perf regression tests in `src-tauri/tests` (30 integration test files, all behavioural). Recommendation: add `divan` or `criterion` benches for the pure hot paths, which are easy to isolate: `paging::collect_stack_folder_entries` over a 10k-entry temp dir, `stack_git_status_from_porcelain` and `parse_git_numstat_output` on recorded 1 MB outputs, `rank_apps`/`best_match` over 2k synthetic entries, `decode_terminal_output_chunk`, `snipping::clipboard::png_rgba` and `encode_rgba`, `BoundedStringCache` get/insert, and `scale_rgba`. Track the results in CI (for example `cargo bench -- --save-baseline`, or `iai-callgrind` on Linux for instruction counts on the pure parts).

#### J. Build, Cargo profile & dependencies

- **RS-53: No Cargo profile tuning** (Medium, S). Evidence: `src-tauri/Cargo.toml` has no `[profile.*]` sections, so release uses the defaults (`opt-level=3`, `lto=false`, `codegen-units=16`, `panic="unwind"`, `debug=false`, `strip="none"`). The release exe is 49.8 MB. Recommendation, with trade-offs:
  ```toml
  [profile.release]
  lto = "thin"          # ~5-15% smaller/faster; "fat" for final builds at higher link time
  codegen-units = 1     # better inlining; slower release builds
  debug = "line-tables-only"  # PDB symbols for crash dumps without full debuginfo cost
  strip = "symbols"     # or keep PDB separate (MSVC already does)
  # panic = "abort"     # only if no code relies on catch_unwind/JoinHandle::join Err; many sites do (e.g. `join().is_err()` in shutdown_workers.rs) - keep unwind.

  [profile.dev.package."*"]
  opt-level = 2         # ORT/ndarray/tokenizers/png/flate2 are unusably slow at opt-level 0; app crate stays fast to compile

  [profile.dev]
  debug = "line-tables-only"  # faster links for a 75 MB debug exe
  ```
  Also evaluate `mimalloc` as `#[global_allocator]`. This codebase is allocation-heavy (Strings, `format!`, JSON `Value` round-trips, data URLs), and mimalloc typically gives a 5-20% throughput win on such workloads on Windows, where the system heap is slow under multi-threaded contention. The cost is about 200 KB and a C build dependency.

- **RS-54: Heavy transitive dependencies for one feature** (Medium, M). Evidence: `cargo tree` shows `parakeet-rs v0.3.7` → `ort v2.0.0-rc.13`, `tokenizers v0.23.2`, `ndarray`, `realfft`, `hound`, `eyre`. 638 crates are in `Cargo.lock`. `tokenizers` with default features pulls `onig` (C build) and `esaxx-rs` (C++), and Parakeet uses a plain `vocab.txt` (`resources/speech-models/*/vocab.txt`), so a full HF tokenizers stack is likely unnecessary. ORT is statically linked into the main binary, which also inflates every self-spawned helper (RS-18, RS-19). Recommendation: put speech behind a Cargo feature (`speech`, on by default) so dev builds and CI for unrelated work can skip ORT. Check whether `parakeet-rs` allows `default-features = false` for tokenizers. Consider `ort` with `load-dynamic` (ship `onnxruntime.dll` next to the exe and load it at first speech use), which takes about 20-30 MB off the exe and off every helper process. Also check: `zip` with `deflate` and `flate2` plus `tar` may duplicate inflate backends (miniz_oxide vs zlib-rs), so unify them on `flate2` with the `zlib-rs` backend.

- **RS-55: Build tooling is non-standard and the build script parses `main.rs` text** (Low, S). Evidence: `.cargo/config.toml` (`[build] rustc-wrapper = ".local/rustc-build-script-wrapper.exe"`, the "Blaze" wrapper). `build.rs:16-31` parses `include_str!("src/main.rs")` for the `generate_handler!` list and rewrites `permissions/legacy-shell.toml`. `build.rs:36` has `rerun-if-changed=src/main.rs` only, so this is fine for incremental builds. It is fragile but documented. Recommendation: no action is needed for performance. If commands move out of `main.rs` (RS-46), keep the inventory in one `commands.rs` macro (`macro_rules! shell_commands { … }`) that both `generate_handler!` and build.rs consume.

#### K. Smaller hot-path smells

- **RS-56: `count_untracked_file_lines` canonicalizes the repo root once per untracked file and reads whole files** (Low, S). Evidence: `stack_popup/git_status.rs:1355-1394` (`canonicalize_existing_path(repo_root)` at `:1376` inside the per-file function; `std::fs::read` of up to 1 MiB per file, 256 files, 8 MiB total) to count newlines for untracked "+N" stats. Recommendation: canonicalize the root once per refresh and pass it in. Count newlines with a streaming `BufReader` plus `memchr::memchr_iter` (memchr is already a transitive dependency) instead of loading whole files. Consider dropping untracked line counts or computing them lazily when the row is expanded.

- **RS-57: `suggest_stack_paths` reads the entire directory, calls `is_dir()` per entry, and lowercases in the comparator** (Low, S). Evidence: `stack_popup.rs:1452-1482`. `path.is_dir()` is a stat per entry where `entry.file_type()` is free; `name.to_lowercase()` runs per entry and again in `sort_by`; the code collects all matches and then truncates to ≤50. Recommendation: use `entry.file_type()`, a cached sort key, and a bounded heap. Make the command `async` (RS-01).

- **RS-58: `windows_icon_cache_key` and `cache_token` allocate per lookup** (Low, S). Evidence: `task_windows/icons.rs:94-133` builds a `String` per lookup (lowercased path plus `format!("icon:{:p}")`) for every taskbar window every second. Recommendation: use a `(isize hwnd, isize hicon, u64 path_hash)` tuple key (Copy, no allocation).

- **RS-59: Clone and allocation hotspots in snapshot and diagnostic code** (Low, S). Evidence: `search/mod.rs:209-232` (`apps_run.timing.clone()`, `health.clone()` and `provider_timings.clone()` per phase), `task_windows/windows.rs:353/368` (`windows.clone()` twice per second), `stack_popup/terminal.rs:984` (`session_id.clone()` per 4 KiB chunk), `paging.rs:96` (`path.clone()` then moved). Each is minor; together they show "clone to satisfy the borrow checker" being used as the default. Recommendation: use `Arc<str>` for IDs shared across threads and events (session IDs, run IDs, labels). Build payload structs that borrow (`#[derive(Serialize)] struct Chunk<'a> { session_id: &'a str, text: &'a str }`), since serde serializes borrowed data just as well.

- **RS-60: The keyboard hook path is well-built; keep it that way** (Info). Evidence: `windows_key_hook.rs:205-236` uses a thread-local `RefCell` with `try_borrow_mut`, no locks, no allocation and no IPC in the LL hook callback, with emission moved to a separate dispatch thread (`:276-300`). This is the right pattern and a template for the other native callbacks (folder-watch `on_change`, WinEvent hooks). Other good patterns already present: generation-fenced latest-only search (`search/mod.rs:138-160`), `GIT_OPTIONAL_LOCKS=0` for read paths (`git_status.rs:1630-1635`), `ReadDirectoryChangesW` with 200 ms debounce instead of scanning (`folder_watch/native.rs:25-26`), bounded paging sessions with byte budgets (`paging.rs:12-19`), `ipc::Response` for snip images (`snipping/runtime.rs:389`), and job objects with kill-on-close for helpers.

### Big bets

1. **One native "services" layer with explicit executors** (L). Replace about 33 ad-hoc threads and about 147 UI-thread sync commands with:
   - a tokio runtime (already present via Tauri) for orchestration, timers and cancellation (`tokio::time`, `CancellationToken`, `JoinSet`);
   - one `spawn_blocking`-style pool for filesystem work;
   - three long-lived apartment threads: a COM STA for shell, links, icons and the clipboard; a COM MTA for audio; and a Win32 message-loop thread for WinEvent and shell hooks;
   - a `WorkerGroup` with mandatory names for shutdown draining.

   Every `#[tauri::command]` becomes a thin `async` shim. Expected effect: no more UI-thread stalls (RS-01, 02, 04, 08), fewer threads, and simpler shutdown.

2. **Stop shipping images through JSON** (M-L). Add an `IconService` with an O(1) LRU, `SHGFI_SYSICONINDEX` or extension keys, and PNG generation on the STA worker, plus a `jsicon://` async URI-scheme protocol serving bytes with immutable caching. Window previews and thumbnails use the same scheme or `ipc::Response`. Payloads (taskbar snapshot, process list, search, stack items) shrink by an order of magnitude, the four caches merge into one, and the webview's HTTP cache does deduplication (RS-25, 26, 29, 30, 31, 40).

3. **Event-driven taskbar and appbar instead of polling** (M). Use WinEvent/shell hooks (`EVENT_OBJECT_CREATE/DESTROY/SHOW/HIDE/NAMECHANGE`, `EVENT_SYSTEM_FOREGROUND`, `HSHELL_*` via `RegisterShellHookWindow`) to feed a diffed window model. Emit deltas only to the bottom bar, and use `ABN_FULLSCREENAPP` for fullscreen. Keep a 10 s safety-net rescan. This removes the 1 Hz full scan with up to 800 `OpenProcess` calls, the 4 Hz and 10 Hz guards and the 20 Hz System Info tick (RS-05, 06, 31).

4. **Git: one runner, fewer spawns, optional gitoxide** (M). Make a single `git` module with `WaitForSingleObject`-based supervision and `CREATE_NO_WINDOW`. Use `status --porcelain=v2 --branch -z` as the primary query, cache repo discovery and config, and run the numstats in parallel. Next, `gix` for discovery, HEAD, config and ahead/behind, keeping git.exe for status and mutations. Expected: Stack git refresh drops from roughly 0.4-0.8 s (7 sequential spawns plus a 50 ms poll each) to one or two spawns of about 30-80 ms (RS-07, 13-17).

5. **Terminal transport rewrite** (M). Use a frame-coalesced (about 16 ms or 64 KiB) PTY reader that sends raw `Uint8Array` over `tauri::ipc::Channel`, plus a per-session writer thread, a per-session lock, and a byte-bounded scrollback ring for reattach. Drop the duplicate `sync_channel` path and the Rust-side UTF-8 decoding (RS-33, 34, 10).

6. **Speech on demand** (M). Load lazily, unload when idle, use explicit ORT thread and arena options with a cached optimized graph, an RT-safe capture ring and `rubato` resampling. Optionally use `ort` `load-dynamic` and a `speech` Cargo feature to shrink the main exe from 49.8 MB, which also speeds up every self-spawned helper (RS-18, 41, 42, 54).

7. **Observability first, then tune** (M). Add `tracing` with spans on the about 10 hot paths listed in RS-51, `divan` benches for the pure kernels (RS-52), and Cargo profile and allocator tuning (RS-53). Replace source-text tests with behavioural seams (RS-50) so the refactors above don't break structural tests.

8. **Typed errors and shared utilities** (L, incremental). Use `thiserror` per subsystem and a `win/` utility module (wide strings, job objects, COM apartments, HICON→PNG, atomic persist), and delete the test-only legacy search tree. This reduces the about 60k production lines meaningfully and makes performance work less risky (RS-46-49).

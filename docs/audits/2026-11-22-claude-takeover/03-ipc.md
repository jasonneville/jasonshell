### Findings

Severity: Critical / High / Medium / Low. Effort: S (< 1 day), M (1–5 days), L (> 1 week).

#### A. Threading and command execution model

- **IPC-01: About 146 of 228 commands are sync, so they run on the single Tao/WebView2 UI thread that all 19 webviews share** (High, M)
  - Evidence: no `#[tauri::command(async)]` in the repo. The parser counts 146 sync and 82 async. In Tauri 2, a sync `#[tauri::command]` runs inline in the IPC handler on the main thread. All 19 shell webviews (`shell_windows.rs:126-157`, plus the notification window at `quick_command_notification.rs:86`) share that one Win32 message pump.
  - Problem: any slow sync command freezes input, painting, and IPC for the top bar, bottom bar, and every open panel at once. In a shell replacement that shows up as a frozen taskbar. Several sync commands do disk, child-process, COM, cross-process, or sleep work (table above).
  - Recommendation: make "async by default" a rule. Mark every command `async` (or `#[tauri::command(async)]`). Wrap blocking bodies in `spawn_blocking`. Hop to the UI thread only for HWND or window APIs that need it, through `run_on_main_thread` with a oneshot reply. Add a build-time lint, for example a `build.rs` scan or a proc-macro wrapper, that rejects a new sync command unless it is on an explicit `MAIN_THREAD_OK` allowlist (window show/hide/resize). The repo already parses `main.rs` in `build.rs:15-31`, so the check fits there.

- **IPC-02: `read_stack_folder` enumerates the whole directory synchronously on the UI thread** (High, S)
  - Evidence: `stack_popup.rs:392-405` (sync). `paging.rs:57-63` calls `collect_stack_folder_entries` for the whole folder when `offset == 0`. The caps are `MAX_FILESYSTEM_LISTING_ENTRIES = 10_000` and `MAX_STACK_FOLDER_SESSION_BYTES = 32 MiB` (`paging.rs:14,19`).
  - Problem: Downloads, network shares, OneDrive placeholders, and AV-scanned folders can take hundreds of ms to seconds. Pagination helps only after the full enumeration has finished on the main thread.
  - Recommendation: make it `async` with `spawn_blocking`. Better, stream the first page as soon as about 80 entries are ready and continue the enumeration in the background into the session, sending a `Channel<FolderPageDelta>`. Keep the session ID contract.

- **IPC-03: Task-window activate and close sleep on the UI thread for up to about 0.5–1.5 s** (High, S)
  - Evidence: `activate_task_window` is sync (`task_windows/mod.rs:193`) and runs `wait_for_windows_restore` (10 × 50 ms sleeps, `actions.rs:19-22,199-208`). `close_task_window` is sync (`mod.rs:225`) and runs `wait_for_window_close` up to three times (`actions.rs:311,326,382,716-722`).
  - Problem: clicking a taskbar button for a minimized window can block the whole shell for up to 500 ms. Closing a window that shows a "Save changes?" prompt can block for more than 1 s. The same logic in `task_gallery::activate_task_gallery_window` / `close_task_gallery_previewed_window` is `async` (`task_gallery.rs:631,721-731`), so it runs on a Tokio worker instead. The two paths give one operation two different threading behaviours.
  - Recommendation: one async implementation with `spawn_blocking` for the verify loops. Return immediately with an "accepted" result and report final state through the existing `taskbar:windows-snapshot` push.

- **IPC-04: `list_pinned_taskbar_apps` blocks the UI thread on a thread it spawns, and re-extracts every icon on every call** (High, S)
  - Evidence: the command is sync (`launchers.rs:13-16`). `run_in_sta` calls `thread::spawn(...).join()` (`launchers.rs:516-538`). Each `.lnk` goes through `extract_icon_data_url` to PNG to base64 with no cache (`launchers.rs:128-139,727-728`).
  - Problem: STA isolation is correct, but `join()` keeps the main thread blocked for the whole time. `taskbar:refresh-launchers` repeats the full cost each time.
  - Recommendation: make it async. Use a long-lived STA worker thread (a single COM apartment fed by an mpsc job queue) instead of a spawn per call. Cache icons by (path, mtime) and return icon keys (see IPC-16).

- **IPC-05: `get_workspace_git_status` runs `git status` as a child process synchronously** (Medium, S)
  - Evidence: `dev_tools/git_status.rs:22-35`, sync, `Command::new("git")...output()`.
  - Problem: git on a large repo, or with a cold FS cache, takes seconds. The stack-popup git commands are async and use `spawn_blocking` (`stack_popup/git_status.rs`), so this path is inconsistent with them.
  - Recommendation: make it `async` with `spawn_blocking` and a timeout, as the stack git path does. Or delete it if `get_stack_git_*` supersedes it (consolidation, IPC-10).

- **IPC-06: Five async commands do blocking work directly on Tokio workers** (Medium, S)
  - Evidence: the parser found no `.await` or `spawn_blocking` in `start_stack_file_drag` (`stack_popup.rs:1626`), `hide_task_gallery`, `activate_task_gallery_window` (`task_gallery.rs:631`, which calls the sleeping `task_windows::activate_task_window`), `show_task_gallery_window_context_menu`, and `close_task_gallery_previewed_window` (`task_gallery.rs:721-731`, close-verify sleeps).
  - Problem: Tauri's async runtime has a fixed worker pool. Blocking sleeps there delay every other async command (search, git, icons, process list).
  - Recommendation: `spawn_blocking` for these bodies, or `run_on_main_thread` where an HWND or DoDragDrop requires the UI thread. Add a clippy-style lint: async command bodies must contain `.await`.

- **IPC-07: Settings are read from disk and parsed on every call, mostly from sync commands** (Medium, S)
  - Evidence: `load_shell_settings_for_app` reads the path and parses it each time (`settings.rs:471-474`). It is called from 18 non-test sites, including sync `load_shell_settings` (`settings.rs:385`), `list_workspaces` (`workspaces.rs:220`), `run_quick_command` (`quick_commands.rs:403`), and `spawn_workspace_task` (`task_runner.rs:128`).
  - Problem: repeated disk I/O and JSON parsing on the UI thread. There is also no single in-memory source of truth for settings, so each surface re-fetches.
  - Recommendation: keep an `ArcSwap<ShellSettings>` (or `RwLock`) in managed state, loaded once and replaced atomically on save. Push a `settings:changed {revision}` event to consumers instead of having them re-read.

#### B. Contract and type safety across the boundary

- **IPC-08: Five hand-maintained command inventories have already drifted** (High, M)
  - Evidence:
    - `main.rs:142-369`: 226 handlers. This is the runtime authority, and `build.rs:15-31` parses it as text.
    - `contracts.rs::commands` (`contracts.rs:47-266`): 216. Missing: `capture_speech_paste_target`, `get_speech_model_status`, `import_speech_model`, `import_speech_model_folder`, `resize_search_panel`, `resize_shell_bar`, `run_task_window_action`, `run_taskbar_launcher_action`, `show_centered_search_panel`, `trigger_system_power_action`.
    - `src/ipc/commands.ts:3-223`: 219. Missing: `list_audio_devices`, `list_audio_sessions`, `set_app_session_mute`, `set_app_session_volume_percent`, `set_default_audio_device`, `set_master_mute`, `set_master_volume_percent`.
    - `permissions/legacy-shell.toml`: 199, generated.
    - `stack_popup/auth.rs:74-419` `STACK_GUARDED_COMMANDS`: `#[cfg(test)]` and **referenced nowhere** (grep finds only its definition).
  - Problem: nothing cross-checks Rust and TS. `tests/contractsSettings.test.mjs:150-180` only regex-matches a handful of names. Drift is caught at runtime ("command not found") or not at all.
  - Recommendation: keep one declarative registry and generate the rest from it (see Big Bet 1). Short term, add a single `cargo test` that parses `generate_handler!`, `contracts::commands::ALL`, and `src/ipc/commands.ts`, and asserts the three sets are equal (allowing an explicit `RUST_ONLY` list).

- **IPC-09: The caller-ACL documentation table is dead and wrong in at least 7 places** (High, S)
  - Evidence: `auth.rs:74-419` declares caller lists that disagree with runtime code:
    - `COPY_STACK_ITEMS` lists `[STACK_POPUP]` (`auth.rs:181-184`). Runtime allows `STACK_POPUP, TERMINAL_PANEL` (`stack_popup.rs:1610-1617`).
    - `NEW_STACK_TEXT_FILE` lists `[STACK_POPUP]` (`auth.rs:217-220`). Runtime allows `+TERMINAL_PANEL` (`stack_popup.rs:2089-2096`).
    - `READ_STACK_FOLDER` lists `[STACK_POPUP]` (`auth.rs:146-149`). Runtime has **no window parameter, so no check** (`stack_popup.rs:393-398`).
    - `SUGGEST_STACK_PATHS` (`auth.rs:150-153`): no check at runtime (`stack_popup.rs:1452-1456`).
    - `RESOLVE_STACK_ITEM_ICONS` (`auth.rs:154-157`): no check (`stack_popup.rs:1485-1488`).
    - `SHOW_STACK_POPUP` lists `[TOP_BAR]` (`auth.rs:109-112`): no check (`stack_popup.rs:294-301`).
    - `PIN/UNPIN/REORDER_PINNED_STACK_FOLDERS` (`auth.rs:90-108`): no check (`stack_popup.rs:262-292`).
  - Problem: reviewers or agents reading `auth.rs` will believe these commands are guarded when they are not. The table gives false assurance.
  - Recommendation: delete the table, or make it the **runtime** source. Implement `authorize(window, &COMMAND_POLICY[cmd])` so call sites cannot disagree with the table, and generate the capability JSON from it (Big Bet 4).

- **IPC-10: No TS type generation. 364 hand-written TS types mirror about 300 Rust `Deserialize` and many more `Serialize` structs** (High, L)
  - Evidence: no `specta`, `tauri-specta`, `ts-rs`, or `typeshare` in `Cargo.toml` or `package.json`. 303 `derive(...Deserialize...)` and 370 `rename_all = "camelCase"` in Rust. 364 exported types in `src/lib` and `src/ipc`. 101 `invoke(IPC_COMMANDS.x` calls are untyped (`Promise<unknown>`). 34 hand-rolled `unknown` validators exist.
  - Problem: field renames, Option-ness, and enum variant changes compile on both sides and fail silently at runtime. Casing is mostly camelCase, but 4 enums use other casings (`diagnostics.rs:17` lowercase, `process_manager/system_info.rs:6,315,324` snake_case, `providers.rs:35` kebab-case), so per-type knowledge is needed.
  - Recommendation: adopt `tauri-specta` v2 (specta `rc`) to emit `bindings.ts` with typed `commands.*` and `events.*`, plus a CI check that `bindings.ts` is up to date. Or, more conservatively, `ts-rs` for payload types only, keeping `IPC_COMMANDS`. Keep the runtime validators only for untrusted or edge payloads.

- **IPC-11: The error contract is `Result<T, String>` everywhere, and callers branch on English text** (Medium, M)
  - Evidence: every command except one returns `Result<_, String>`. Stale-context control flow is signalled by error strings such as `Err("inactive or stale context")` (`process_manager.rs:82,86`), `"Unauthorized caller for command {command}"` (`auth.rs:30`, 32 sites), and `"quick command is no longer running"`. The frontend does substring checks, e.g. `TopBar.svelte:214` uses `code.includes('timeout')`, plus 41 `String(error)` / `instanceof Error` sites.
  - Problem: there is no stable machine-readable code, so i18n, telemetry, and retry policy are impossible. Expected staleness and real failures look the same. Errors also cannot carry structured data, such as a retry-after or a fresh revision.
  - Recommendation: add a crate-wide `#[derive(Serialize, specta::Type)] #[serde(tag="code")] enum IpcError { Stale{current:u64}, Unauthorized, NotFound, Busy, Invalid{field}, Io{message}, Internal }` implementing `From<String>` for gradual migration. Model expected staleness as `Ok(Outcome::Stale)` rather than `Err`.

#### C. Security model at the boundary

- **IPC-12: The Tauri ACL is effectively off for 88% of commands. One "legacy" capability grants 199 commands to 18 windows** (High, M)
  - Evidence: `build.rs:41-52` writes `allow-legacy-shell-commands` containing every registered command except 27 snip, system-info, hotkey, exit, notification, and local-drop commands. `capabilities/legacy-shell.json` grants it to 18 windows (`top-bar` through `context-menu-overlay`, including `calendar-panel`, `speech-indicator`, and `tray-panel`).
  - Problem: security rests entirely on Rust-side label checks, and about 93 commands take no `WebviewWindow` at all, so they cannot check anything. Among them, `open_shell_path` and `launch_app_path` (`shell_paths.rs:3-24`, ShellExecute of a renderer-supplied path), `read_stack_folder`, `suggest_stack_paths`, `pin_stack_folder`, `invoke_system_tray_icon`, `activate/maximize/close_task_window`, `set_*volume*`, `spawn_workspace_task`, `cancel_workspace_task`, `save` paths in `workspaces.rs`, and `publish_search_panel` can be called from any shell window, including the calendar and speech indicator. The per-window capability files describe abilities they do not grant. For example, `audio-panel.json` says "volume/device controls" but lists only `core:default`, and the real grant comes from legacy-shell.
  - Recommendation: generate per-window capability files from a single policy table (command to caller labels). Drop `legacy-shell`. Keep the Rust `authorize` call as defence in depth. Exposure is moderated by CSP `script-src 'self'` (`tauri.conf.json`) and local-only content, but a single XSS in any renderer (for example a file name or git commit message rendered with `{@html}`) currently reaches ShellExecute.

- **IPC-13: Every window has `core:default`, which includes JS `emit`/`emitTo`, so any renderer can forge Rust-originated events to any other window** (Medium, M)
  - Evidence: 17 of 22 capabilities include `core:default` (`capabilities/*.json`). JS code relies on renderer-to-renderer events, e.g. `stackPopup.ts:400-412` (`emit(STACK_PINS_UPDATED)`, `emitTo(STACK_POPUP_LABEL, STACK_POPUP_OPEN_EVENT, payload)`) and `SearchPanelSurface.svelte:184-345`. Events Rust treats as authoritative share that namespace, e.g. `stack-terminal:output`, `taskbar:windows-snapshot`, and `stack-popup:folder-changed`. Listeners filter only by payload fields (`sessionId`, `watchId`).
  - Problem: the elaborate nonce and caller checks on commands do not apply to events. A compromised panel can inject fake terminal output, a fake taskbar snapshot, or an `open` request carrying an arbitrary path. The quick-command banner capability correctly omits `core:default` and uses a `Channel` (`quick-command-notification.json`, `quick_command_notification.rs:237`), which shows the team already knows the safer pattern.
  - Recommendation: replace `core:default` with an explicit minimal set per window (`core:event:allow-listen`, `allow-unlisten`, and `allow-emit-to` only where a JS-to-JS hop is needed). Move Rust-to-renderer streams to `Channel`s, which renderers cannot spoof. Prefix Rust-only events (for example `rs:`) and reject JS emits of that prefix in a small `on_event` hook, or keep the namespaces separate.

- **IPC-14: `publish_search_panel` takes an untyped `serde_json::Value` from any window, relays it, and can panic** (Medium, S)
  - Evidence: `search_panel.rs:170-185`: no window parameter, `payload: Value`, stored and re-emitted to `search-panel`. `store_search_panel_payload` uses `.lock().expect("search panel runtime state is poisoned")` (`search_panel.rs:194-197`).
  - Problem: there is no schema, no size bound, and no caller check. A panic in a sync command on the UI thread can take down the shell process.
  - Recommendation: use a typed `SearchPanelPayload` with `deny_unknown_fields`, a size cap, and a `TOP_BAR` caller check. Replace `expect` with an error. Long term, remove the relay (IPC-21).

- **IPC-15: The build script edits a tracked source file and parses `main.rs` with string splitting** (Low, S)
  - Evidence: `build.rs:15-31` uses `split(".invoke_handler(tauri::generate_handler![")`, and `build.rs:49-52` calls `fs::write("permissions/legacy-shell.toml", ...)`. The 226 autogenerated permission files are committed. This audit's git snapshot shows 5 of them modified and 2 untracked.
  - Problem: a formatting change in `main.rs` (a comment containing `])`, or cfg-gated entries) silently changes the ACL. Building rewrites tracked files, which causes noisy diffs and merge churn. The "permission sprawl" of 226 files is generated noise rather than hand-maintained, but it still clutters review.
  - Recommendation: produce the inventory with a macro (for example a `commands!{}` macro that expands to both `generate_handler!` and a `const COMMANDS: &[&str]`). Write generated permissions under `OUT_DIR` or `gen/` (already gitignored) where tauri-build allows. Otherwise, mark `permissions/autogenerated/` as `linguist-generated` and add a CI check for staleness.

#### D. Serialization and payload efficiency

- **IPC-16: Icons travel as base64 PNG data URLs inside JSON on hot paths: process list every 1 s, taskbar snapshots, launchers, tray** (High, M)
  - Evidence: `ProcessInfo.icon_data_url` (`process_manager.rs:107,905-918`). `ProcessManagerSurface.svelte:56,181-185` polls `list_processes` every **1,000 ms**. `TaskbarWindow.icon_data_url` (`task_windows/mod.rs:12`) is included in every `taskbar:windows-snapshot` (`task_windows/windows.rs:364-371`). Launchers, tray icons, and stack icons are encoded the same way (`launchers.rs:727`, `system_tray.rs:297`, `stack_popup/icons.rs:142`).
  - Problem: base64 adds 33%, and JSON string escaping and parsing cost more on top. A process table of about 300 rows with repeated icons (for example 30 `chrome.exe` processes) re-sends the same strings every second. Rust caches the PNG, but serialization, transfer, `JSON.parse`, and `<img src>` re-decode are paid every tick. Events are delivered by evaluating a script that embeds the JSON payload (`tauri/src/event/listener.rs:269-293`, `webview.emit_js`), which is expensive for large literals.
  - Recommendation: serve icons through a custom async URI scheme (`register_asynchronous_uri_scheme_protocol("shellicon", ...)`) keyed by a content hash or by `(path, mtime)`. Payloads then carry `iconKey: "shellicon://localhost/<hash>.png"`. Add `shellicon:` to CSP `img-src`. The browser caches and decodes once, and rows shrink to a few bytes. Alternatively, return icons separately as `tauri::ipc::Response` raw bytes on demand. The repo already does this for snips (`snipping/runtime.rs:389-392`, `src/lib/snipping.ts:98-107`).

- **IPC-17: Terminal output is double-delivered (an emit per 4 KiB read plus a polling queue), UTF-8 decoded in Rust, and JSON-escaped** (High, M)
  - Evidence:
    - Reader thread: every `read()` of up to 4096 bytes produces a String chunk, then `emit_to(target_label, "stack-terminal:output", chunk)`, **and** a `try_send` into a `sync_channel(1024)` for polling (`stack_popup/terminal.rs:961-1031`, `904`).
    - Polling: `TerminalPanelSurface.svelte:2085-2091` runs a 1,000 ms `setInterval` **per runtime** calling sync `poll_stack_terminal_session` (`stack_popup.rs:2290-2306`), which takes the global `Mutex<StackPopupRuntimeState>` (`terminal.rs:525-537`). `StackTerminalPane.svelte:519-527` polls every 1,500 ms as a "watchdog".
    - Deduplication is done in JS by `TerminalSequenceTracker` (`src/lib/terminalSequenceTracker.ts`).
  - Problem: ANSI-heavy output (ESC becomes `\u001b`, six bytes per ESC in JSON) inflates the payload. Bulk output (`cat`, build logs) produces thousands of emits per second, each a script evaluation in the webview. There is no coalescing. Polling adds steady-state main-thread wakeups and global-lock contention for every open terminal even when idle. The dual path needs the sequence-tracker machinery to stay correct.
  - Recommendation: give each session a `tauri::ipc::Channel<InvokeResponseBody>` created by the renderer and passed into `start_stack_terminal`. The reader thread coalesces into frames (for example flush at ≥16 KiB or every 8–16 ms) and sends **raw bytes** (`InvokeResponseBody::Raw`). xterm.js accepts `Uint8Array` and decodes UTF-8 itself, so Rust-side UTF-8 handling (`decode_terminal_output_chunk`, `terminal.rs:1034-1060`) goes away. Keep a bounded ring buffer for replay on re-attach instead of polling. Delete the poll loop and the sequence tracker once Channel delivery is in-order and lossless, which Channels guarantee per channel.

- **IPC-18: Terminal and task output is silently dropped under backpressure, and task output corrupts UTF-8** (Medium, S)
  - Evidence: `match tx.try_send(...) { Err(TrySendError::Full(_)) => {} ... }` (`terminal.rs:997-1003`). When 1,024 chunks are queued, polling consumers lose data with no gap marker. Task runner: `String::from_utf8_lossy(&buffer[..bytes])` per read (`dev_tools/task_runner.rs:279-297`) splits multibyte characters at chunk boundaries and produces replacement characters, unlike the terminal reader's pending-byte decoder.
  - Problem: logs look corrupted for non-ASCII output, such as paths with accents or emoji in npm output. Drops cannot be detected.
  - Recommendation: send raw bytes over a Channel (IPC-17). If text must stay, reuse the terminal's incremental decoder (or `encoding_rs`/`utf8::Incremental`). Emit an explicit `{gap: n}` marker when dropping.

- **IPC-19: `task:output` is broadcast app-wide, once per read** (Medium, S)
  - Evidence: `dev_tools/task_runner.rs:156` (`emit(TASK_STARTED_EVENT)`), `297` (`emit(TASK_OUTPUT_EVENT)`), `339` (`emit(...completed)`).
  - Problem: every webview with a listener gets every chunk, with no target, coalescing, or batching. The only consumer is `src/lib/devTools.ts:111`.
  - Recommendation: use a per-task `Channel` returned to the caller, or at least `emit_to` the owning surface with coalesced frames.

- **IPC-20: Global `emit` is used where a single target was intended. `window.emit(...)` broadcasts in Tauri 2** (Medium, S)
  - Evidence: Tauri 2 `Emitter::emit` "emits an event to all targets" whatever the receiver (`tauri-2.10.3/src/lib.rs:940-955`). Call sites that look window-scoped but broadcast:
    - `stack_popup/clipboard.rs:192,360` and `stack_popup.rs:2004,2051,2490` (`window.emit(STACK_FILE_OPERATION_PROGRESS, ...)`, high-frequency progress)
    - `stack_popup.rs:328` (`popup.emit(STACK_POPUP_CLOSE_REQUESTED)`)
    - `stack_popup/popup_window.rs:119` (`"stack-popup:open"`)
    - `task_preview.rs:307,328` (`preview_window.emit(TASK_PREVIEW_UPDATE_EVENT, payload)`, which carries a base64 PNG preview)
    - `process_manager.rs:51,283`, `audio_panel.rs:60`, `calendar_panel.rs:60`
    - In total, 28 global emits against 63 `emit_to`.
  - Problem: these are wasted evaluations in any other webview that listens to the same name, and they can trigger cross-surface handlers by accident. For example, two stack-browser-capable surfaces would both react to progress events.
  - Recommendation: use `emit_to(EventTarget::webview_window(label), ...)` or `window.emit_to(window.label(), ...)`. Add a clippy `disallowed-methods` entry for `tauri::Emitter::emit` with an allowlist module for true broadcasts.

- **IPC-21: JS global `listen()` receives every `emit_to`, whatever the target, so targeted delivery is defeated on the receiver side** (Medium, S)
  - Evidence: `@tauri-apps/api/event.js:69-81` defaults to `target: { kind: 'Any' }`. Rust `match_any_or_filter` returns true for `EventTarget::Any` (`tauri-2.10.3/src/event/listener.rs:306-311`), so an `Any` listener in window A matches an event sent `emit_to("B")`. 17 files import global `listen`. Only 4 sites use window-scoped `getCurrentWindow().listen` (`StackPopupSurface.svelte:417-429`).
  - Problem: `stack-terminal:output` sent `emit_to(terminal-panel)` is also evaluated in `stack-popup` (`StackTerminalPane.svelte:195`), and the reverse, for every chunk. `stackPopup.ts:400-401` sends the same pins update by both `emit` and `emitTo(top-bar)`, so the top bar's global listener likely fires twice.
  - Recommendation: one wrapper, `listenHere(event, handler)`, that uses `getCurrentWebviewWindow().listen` (target equals own label) for all Rust-targeted events. Ban bare `listen` with an ESLint `no-restricted-imports` rule except for intentional broadcasts.

- **IPC-22: Search results cross the boundary three times: Rust to top bar, top bar to Rust, Rust to search panel** (Medium, M)
  - Evidence: `search_engine` emits progress globally (`search/mod.rs:78-90`, `app.emit(SEARCH_ENGINE_PROGRESS_EVENT, payload)`). The top bar then calls `publish_search_panel` with the composed payload as `Value` (`search_panel.rs:170-185`), Rust stores it and `emit_to(search-panel)`, and the panel can also pull `get_search_panel_payload` (`search_panel.rs:187-192`). Keystrokes and selection go back by JS `emitTo(topBarTarget, ...)` (`SearchPanelSurface.svelte:184-345`).
  - Problem: three serialize/parse cycles per result update, an untyped Value hop, and global broadcast of progress. The search panel window is a "dumb view" fed by another renderer, through Rust.
  - Recommendation: have the search panel own the query session. It calls `search_engine` with a `Channel<SearchProgress>` and renders directly. The top bar only forwards the query string. Or let Rust push results with `emit_to(search-panel)` directly from the engine, keyed by a sequence number. In either case, remove `publish_search_panel`.

- **IPC-23: Polling loops that should be push-driven** (Medium, M)
  - Evidence:
    - `ProcessManagerSurface.svelte:181-185`: `list_processes` every 1 s on the Processes tab. The System Info tab polls `get_system_info_snapshot` every 2 s, a cache read (`process_manager.rs:80-88`) whose request carries `after_revision`.
    - `CommandPanelSurface.svelte:1011`: `refreshHistory` every 1.1 s, alongside a `quick-command:run-updated` push listener.
    - `AudioPanelSurface.svelte:74-78`: `get_audio_state` every 2 s (sync COM on the UI thread).
    - Terminal polls (IPC-17).
  - Problem: steady-state IPC traffic and main-thread wakeups, even when nothing changed. For System Info, the producer already knows when its revision changes.
  - Recommendation: Channel subscriptions such as `subscribe_system_info(open_generation, tab_revision, channel)`, where the producer pushes on revision change and the subscription ends when the Channel is dropped or the panel closes. Use `IAudioEndpointVolumeCallback` / `IAudioSessionNotification` to push audio changes. Send process-list deltas keyed by pid, plus an icon key (IPC-16).

- **IPC-24: Task preview fallback captures, PNG-encodes, and base64s on the UI thread, then broadcasts** (Medium, S)
  - Evidence: sync `show_task_window_preview` (`task_preview.rs:97`) leads to `fallback_preview_payload` and `capture_task_window_preview` (`task_preview.rs:243`, `task_windows/previews.rs:24-40`: GDI capture, scale, `encode_png`, base64), then `preview_window.emit` (global, `task_preview.rs:328`).
  - Problem: hovering over a taskbar item whose live DWM thumbnail fails costs tens of ms on the main thread, plus a broadcast of a data URL that can exceed 100 KB.
  - Recommendation: run the capture in `spawn_blocking` and send the bytes as a raw `Response` (renderer pulls `get_task_preview_image(requestId)`) or through the custom scheme. Use `emit_to(task-preview)` only for metadata.

#### E. Event lifecycle and stale-event guards

- **IPC-25: Stale-request guards are reinvented per feature: about 97 ad-hoc counters in TS and dozens in Rust, with mixed types** (Medium, M)
  - Evidence: grep counts identifiers containing nonce, generation, revision, sequence, and epoch at 587/441/473/230/145 in Rust and 283/201/310/467/228 in TS. 97 TS sites do `x = 0` / `++x` / `x += 1` on such counters. 8 local `isCurrent` helpers exist. Rust statics include `COMMAND_PANEL_FOCUS_LOSS_NONCE` (`command_panel.rs:11`), `SETTINGS_BLUR_REVISION` / `PROCESS_MANAGER_BLUR_REVISION` (`main.rs:382-383`), `LATEST_SEARCH_SEQUENCE` (`search/mod.rs:74`), and `TASKBAR_SNAPSHOT_SEQUENCE` (`task_windows/windows.rs:47`). Token types differ: snip generation is a `String` (`snipping/runtime.rs:389`), speech nonce a `number` (`ipc/events.ts:79`), task-gallery nonce `string | null` (`BottomBar.svelte:1312`), System Info uses three numbers (`open_generation`, `tab_revision`, `after_revision`; `process_manager.rs:80`).
  - Problem: each guard has its own edge cases (wraparound, equal-sequence tie-break as in `search_panel.rs:198-210`, focus races), and reviewers must re-verify each one. The complexity is the price of a request/response model applied to what are really subscriptions.
  - Recommendation: one shared primitive pair.
    - Rust: `struct Lease { id: u64, epoch: u64 }` with `LeaseTable<K>` (`begin(k) -> Lease`, `is_current(&Lease)`, `retire(k)`), serialized as `{leaseId, epoch}`.
    - TS: `createLatest<T>()` returning `{ begin(): Token; isCurrent(t): boolean; guard<R>(t, p: Promise<R>): Promise<R | Stale> }`.
    - Using Channels removes most guards outright: when the subscription is replaced, the old Channel is dropped and stops delivering, so no stale check is needed.

- **IPC-26: Two copy-pasted 150 ms focus-loss hide timers in `main.rs`, each spawning a blocking-pool thread to sleep** (Low, S)
  - Evidence: `main.rs:468-500` (settings and process manager, revision atomics) and `main.rs:577-621` (command panel, nonce) both do `tauri::async_runtime::spawn(async { spawn_blocking(|| thread::sleep(150ms)).await; run_on_main_thread(...) })`. Separate focus-loss handlers for quick launch, task gallery, audio, calendar, speech history, and tray follow at `main.rs:502-561`, all as `if window.label() == X && matches!(event, ...)` chains.
  - Problem: a blocking-pool thread is used only to sleep (use `tokio::time::sleep`), the logic is duplicated, and the guards differ slightly (the command panel checks maximize and minimize, the settings panel does not). A 200-line `on_window_event` is hard to audit.
  - Recommendation: a `PanelBehavior` table (label to `{hide_on_blur: Option<Duration>, prevent_close, closed_event, retire: fn}`) and one generic dispatcher using `tokio::time::sleep`. Each panel registers its behavior next to its builder in `shell_windows.rs`.

- **IPC-27: The async-unlisten registrar is duplicated 11 times, and listener error handling varies** (Low, S)
  - Evidence: `registerAsyncUnlistener` / `register` helpers at `AudioPanelSurface.svelte:194`, `BottomBar.svelte:1250`, `CommandPanelSurface.svelte:964`, `ProcessManagerSurface.svelte:401`, `SearchPanelSurface.svelte:100`, `SpeechHistoryPanelSurface.svelte:95`, `StackTerminalPane.svelte:183`, `TaskPreviewSurface.svelte:92`, `TerminalPanelSurface.svelte:471`, `TopBar.svelte:1967`, `TrayPanelSurface.svelte:104`. `TaskGallerySurface.svelte:449-555` uses yet another style (stored promises unwrapped at teardown).
  - Problem: these handle the "disposed before listen resolved" race correctly, but each copy is a chance to get it wrong. Unlisten rejections are handled inconsistently.
  - Recommendation: a single `src/ipc/subscriptions.ts` with `useTauriEvents(scope, [[event, handler], ...])` that returns a disposer, works with Svelte 5 `$effect` teardown, uses window-scoped listen by default (IPC-21), and logs consistently.

- **IPC-28: Event-name constants are scattered and duplicated: 22 Rust consts outside `contracts.rs`, 47 TS consts outside `ipc/events.ts`** (Low, S)
  - Evidence: `"taskbar:windows-snapshot"` is defined in `contracts.rs:524`, `task_windows/mod.rs:94`, `BottomBar.svelte:160`, `TopBar.svelte:359`, and `lib/taskbarUi.ts:5`. `SEARCH_ENGINE_PROGRESS_EVENT` is a local literal in `search/mod.rs:73`. Literal event strings appear in emits (`snipping/runtime.rs:246,281`: `"snip:prepare_bar"`, `"snip:release_bar"`; `popup_window.rs:119`). TS has 79 distinct `ns:name` literals, while `contracts.rs::events::ALL` has 61 and `IPC_EVENTS` has 53, and `IPC_EVENTS` documents itself as a "convenience subset" (`ipc/events.ts:11-13`).
  - Problem: a rename on one side fails silently, because listeners simply never fire.
  - Recommendation: typed event definitions generated from Rust (`tauri-specta` `collect_events!`, or a `#[derive(Event)]` trait with `const NAME`). Until then, add a `cargo test` asserting that every `emit*("...")` literal and every TS `'ns:name'` literal is in `contracts::events::ALL`.

- **IPC-29: Dead and unreachable IPC surface** (Low, S)
  - Evidence: 7 audio commands are registered and ACL-granted but never invoked from TS (`list_audio_devices`, `list_audio_sessions`, `set_app_session_mute`, `set_app_session_volume_percent`, `set_default_audio_device`, `set_master_mute`, `set_master_volume_percent`; `audio.rs:73-127`). `search_system` (`search_sources.rs:94`) is a `#[tauri::command]` that is not registered. `p03_record` and `p03_save_summary` are invoked from `TextEditorProjectionExperiment.svelte:42,90` but not registered. `hide_quick_launch_panel_on_focus_loss` is both a Rust window-event handler (`main.rs:505`) and a renderer command (`QuickLaunchPanelSurface.svelte:141`).
  - Problem: attack surface and maintenance cost with no feature behind it. The 199-command blanket grant (IPC-12) makes it worse.
  - Recommendation: remove or feature-gate these, and generate the "registered but unused" diff in CI.

#### F. API design and naming

- **IPC-30: Mixed argument conventions: flat scalars, `request`, `args`, `payload`** (Low, M)
  - Evidence: the parser classifies commands as no-args 38, flat 1-arg 55, flat 2-arg 34, flat 3–6 args 24, single `request` struct 62, `args` struct 11, others 4. Examples: `resize_stack_terminal(session_id, cols, rows, pixel_width, pixel_height)` (`stack_popup.rs:2226-2234`), `get_system_info_snapshot(open_generation, tab_revision, after_revision)` (`process_manager.rs:80`), and `invoke('show_quick_launch_panel', { args: {...} })` (`BottomBar.svelte:1217`).
  - Problem: flat arguments rely on Tauri's camelCase-to-snake_case key mapping and are not validated with `deny_unknown_fields`. 70 structs do use `deny_unknown_fields`, but flat arguments cannot. Mixing styles makes generated bindings and versioning harder.
  - Recommendation: one `request: XRequest` struct per command (`#[serde(rename_all="camelCase", deny_unknown_fields)]`), with a matching `XResponse`. This pairs with codegen and a macro (Big Bet 1).

- **IPC-31: Naming is inconsistent in verbs and nouns** (Low, S)
  - Evidence: `stack_git_*` (noun first) sits beside `get_stack_git_status`, `get_stack_git_summary`, and `get_stack_git_context`, which overlap. `read_stack_terminal` and `poll_stack_terminal_session` do the same work (`terminal.rs:503-516` wraps the poll). `delete_stack_item` and `delete_stack_items` exist side by side, and the capability explicitly denies the singular one for stack-popup (`capabilities/stack-popup.json`). `set_master_volume` and `set_master_volume_percent` both exist (`audio.rs:83-95`), as do `set_default_audio_device`, `..._input_device`, and `..._output_device`. Event casing mixes `snip:prepare_bar` (snake) with `stack-popup:close-requested` (kebab).
  - Problem: the API is hard to discover, and duplicates must each be secured and kept up to date.
  - Recommendation: use a `domain.verb` scheme (for example `stack.folder.read`, `stack.git.status`, `terminal.write`) and kebab case for all events. Merge the duplicate pairs.

- **IPC-32: The window-management command surface is about 45 near-identical show/hide commands plus per-panel boilerplate** (Low, M)
  - Evidence: `show_X_panel`/`hide_X_panel` for audio, calendar, command, control-plane, settings, speech-history, terminal, tray, quick-launch, search, stack, process manager, task gallery, and task preview (`main.rs:164-225`). Each module builds its window and emits `X:open` / `X:closed`, e.g. `audio_panel.rs:18-64`, `calendar_panel.rs:18-64`.
  - Problem: boilerplate that differs subtly between copies (anchor math, focus rules), multiplied ACL entries, and multiplied blur handling (IPC-26).
  - Recommendation: `show_panel({panel: PanelId, anchor, nonce})` / `hide_panel({panel, nonce})`, with a `PanelId` enum and a per-panel behavior table. Keep specific commands only where the payload is truly specific.

#### G. Startup

- **IPC-33: All 19 webviews are created eagerly at boot, and every one loads the full `index.html` bootstrap** (Medium, M)
  - Evidence: `shell_windows.rs:110-157` builds top, bottom, preview, search, stack, process manager, quick launch, task gallery, control plane, settings, tray, terminal, command, audio, speech history, calendar, context-menu overlay, and speech indicator. `quick_command_notification::install` adds the 19th (`quick_command_notification.rs:86`, `shell_windows.rs:600-615`). The surfaces are code-split by dynamic import (`src/lib/surfaceLoader.ts:13-35`), which is good, but each webview still initializes WebView2, parses `main.ts` and `App.svelte`, applies the theme (`main.ts:1-18`), registers listeners, and in several cases invokes commands on mount (e.g. `TopBar.svelte:1976-1984`: metrics, catalog, search mode).
  - Problem: boot time and resident memory scale with panel count, not with use. Boot-time IPC fan-out (each surface fetching settings, pins, and state on mount) contends for the main thread just when the AppBar is being registered. Rarely used surfaces (calendar, control plane, speech history, audio) need not exist until first open.
  - Recommendation: keep the always-visible surfaces (top, bottom, speech indicator, perhaps the search panel, where first-open latency matters). Create the others lazily on first `show_panel` and hide rather than destroy them afterwards. Measure with the existing `report_shell_surface_runtime_metrics` (`main.rs:741-747`): add per-surface `ready` timestamps from Rust `WebviewWindowBuilder::build` to first `invoke`. - **IPC-34: Boot work in `setup` runs serially on the main thread before the bars are shown** (Low, S)
  - Evidence: `main.rs:642-700` performs these steps in order: create 18 windows, install notifications, install the snip runtime, install settings capture, load hotkey settings from disk, initialize the app index cache, install the Windows key hook, activate the AppBar, and start taskbar hooks and pipelines.
  - Problem: the time to first visible bar includes all of it.
  - Recommendation: show and activate the AppBar for the top and bottom bars first, then defer the other window creation, the app index, and the notification install to a post-first-paint task, triggered by a `surface-ready` invoke from the bars.

### Big bets

1. **A single IPC registry, generated end to end (tauri-specta plus a policy macro).**
   - Each command is declared once, for example `#[shell_command(callers = [STACK_POPUP, TERMINAL_PANEL], thread = blocking, admission = mutation)] async fn copy_stack_items(ctx: Ctx, req: CopyStackItemsRequest) -> IpcResult<()>`.
   - The macro wraps the body in `spawn_blocking` (or `run_on_main_thread` when `thread = ui`), performs caller authorization and graceful-exit admission, and maps errors to `IpcError`.
   - `tauri-specta` exports `bindings.ts` (typed `commands.copyStackItems(req)` and typed `events`).
   - `build.rs` (or a `cargo xtask`) generates per-window capability JSON from `callers`, `contracts.rs` constants, and the TS name map.
   - This removes IPC-08, IPC-09, IPC-10, IPC-11, IPC-12, IPC-15, IPC-28, and IPC-30 together. It also removes about 1,500 lines of hand-written `authorize_stack_command(...)` blocks (123 sites), whose bodies are 10–15 lines each.

2. **Subscriptions over Channels instead of emit plus poll plus guard.**
   - Standardize `subscribe_*(params, channel: Channel<Frame>) -> SubscriptionId` for terminal sessions (raw bytes, coalesced), task output, file-operation progress, folder watch, System Info, process list deltas, audio state, search progress, and the taskbar snapshot.
   - The Rust side holds `Channel` handles in a `SubscriptionTable` and drops them on window `Destroyed` or explicit unsubscribe.
   - The TS side gets one `subscribe()` helper that returns an async iterator or store.
   - This removes the 1 s and 1.5 s terminal polls, the 1.1 s history poll, and the 2 s audio and System Info polls. It also removes the `TerminalSequenceTracker`, most nonce and generation guards (IPC-25), and the event spoofing surface (IPC-13), and it delivers each frame only to its subscriber (IPC-20, IPC-21).

3. **A binary asset plane for images.**
   - One `register_asynchronous_uri_scheme_protocol("shellimg")` serving icons (by content hash), task previews (by request ID), and snips, with `Cache-Control: immutable` for hashed icons.
   - JSON payloads carry only keys.
   - Estimated effect: process-list payloads shrink by roughly 80–95% (rows have about 10 short fields; icons dominate), taskbar snapshots become a few hundred bytes, and the browser deduplicates and caches decoded bitmaps.

4. **Main-thread budget enforcement.**
   - A `UiThreadGuard` wrapper for the few commands that truly need the UI thread, logging any that exceed 8 ms (one frame) through `diagnostics::record_diagnostic`.
   - Make every other command async with `spawn_blocking` by default.
   - Add a test that fails if a registered command is sync and not on the allowlist (the `build.rs` parse already exists).

5. **Least-privilege capabilities.**
   - Replace `legacy-shell.json` and `core:default` with generated per-window capabilities.
   - Isolate the "dangerous" commands (`open_shell_path`, `launch_app_path`, `spawn_workspace_task`, `kill_process`, `trigger_system_power_action`, git push and pull, delete and paste) into named permission sets granted only to their owning surface.
   - Keep the Rust `authorize` call as defence in depth.

6. **Lazy surface lifecycle.**
   - Create on first use, hide instead of destroy, and pre-warm during idle.
   - Track per-surface boot-to-ready timings through the existing runtime metrics command to set budgets.

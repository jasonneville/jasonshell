# Windows Completion Sound Notification for Pi Prompt/Terminal Runs

## 1. Requirements & Constraints

- **REQ-001**: Add an audible Windows notification when a long-running Pi prompt, Windows Terminal command, or equivalent local run stops running.
- **REQ-002**: The notification must trigger only when execution transitions from running to stopped/completed/failed/cancelled, not while idle.
- **REQ-003**: The implementation must be configurable so users can disable the sound.
- **REQ-004**: The implementation must avoid playing sounds repeatedly for the same completed run.
- **REQ-005**: The implementation must support Windows as the primary platform.
- **REQ-006**: The implementation should gracefully no-op on unsupported platforms unless cross-platform behavior already exists.
- **CON-001**: Planning only; do not edit files or move task-board columns during planning.
- **CON-002**: Exact source ownership is unknown from provided context; implementation must begin with repository discovery.
- **CON-003**: Existing test command hint is `pnpm build`.
- **GUD-001**: Use RED-first tests when practical.
- **GUD-002**: Preserve unrelated dirty worktree changes.
- **PAT-001**: Follow existing terminal/prompt lifecycle event patterns discovered in the codebase.
- **PAT-002**: Update durable documentation if behavior, commands, events, persistence, or known risks change.

## 3. Alternatives

- **ALT-001**: Always play a sound for every terminal output completion. Rejected because it risks duplicate sounds and false positives for idle/prewarmed terminals.
- **ALT-002**: Implement only a manual CLI command to play a sound. Rejected because the requested behavior is automatic when a prompt/terminal stops running.
- **ALT-003**: Add a native Windows audio dependency. Rejected unless already present because it increases install complexity and platform risk.
- **ALT-004**: Enable the sound by default. Rejected unless project conventions favor opt-out notifications, because unsolicited audible notifications can surprise users.

## 7. Risks & Assumptions

- **RISK-001**: The lifecycle event may fire multiple times for one run. Mitigation: implement duplicate prevention keyed by run/session id or transition edge.
- **RISK-002**: PowerShell or system sound invocation may fail on locked-down Windows systems. Mitigation: catch failures and never fail the run because sound playback failed.
- **RISK-003**: Audible notifications can annoy users. Mitigation: add a configuration flag and default to disabled unless project conventions clearly indicate opt-out notifications.
- **RISK-004**: Prewarmed idle terminals may look like stopped runs. Mitigation: explicitly test and preserve behavior documented in `docs/terminal-panel-prewarm-idle-policy.md`.
- **RISK-005**: Exact source files are unknown from lightweight context. Mitigation: Phase 1 requires discovery before naming implementation targets.
- **ASSUMPTION-001**: The project is Node/TypeScript or JavaScript-based because package scripts include `pnpm build`. Verify by inspecting `package.json`.
- **ASSUMPTION-002**: Prompt/terminal runs have identifiable lifecycle states. Verify through TASK-002.
